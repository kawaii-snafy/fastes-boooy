# Формат маршрутов (API v1)

Маршрут — это обычный аддон-модуль, который зависит от ядра `FastesBoooy` и
регистрирует данные через глобальную таблицу `FastesBoooy`. Контракт формата
реализован в [`addons/FastesBoooy/Core/Schema.lua`](../addons/FastesBoooy/Core/Schema.lua)
(чистый Lua 5.1, общий для аддона и офлайн-валидатора).

## Структура модуля

```
addons/FastesBoooy_<Name>/
  FastesBoooy_<Name>.toc   -- ## Interface: 16001, ## Dependencies: FastesBoooy
  Route.lua                -- FastesBoooy.RegisterRoute{...}
  Data.lua                 -- (генерируется, make routedata) FastesBoooy.AddRouteData(id, {quests=..., npcs=..., places=...})
  Segments/01_*.lua        -- FastesBoooy.AddSegment(id, {...}) — по файлу на сегмент
```

Файлы грузятся в порядке TOC. `RegisterRoute` должен идти первым.

Маршрут может брать готовые сегменты из **модуля-библиотеки** (например, общий путь Орды
22-60 в `FastesBoooy_Horde`) и добавлять к ним свои классовые шаги — см. раздел
[«Общие сегменты и вставки»](#общие-сегменты-и-вставки).

## Маршрут

```lua
FastesBoooy.RegisterRoute({
    api = 1,                                  -- версия формата (обязательно)
    id = "horde-undead-paladin",              -- [A-Za-z0-9-_]
    title = { ru = "Нежить-паладин 1-60", en = "Undead Paladin 1-60" },
    faction = "Horde",                        -- "Horde" | "Alliance"
    races = { "Scourge" },                    -- raceFile из UnitRace()
    classes = { "PALADIN" },                  -- classFile из UnitClass()
    levels = { 1, 60 },                       -- {от, до}, до 60 (капа уровня Forever)
    version = "1.0.0",
    default = true,                           -- автоматически выбирать для подходящих персонажей
})
```

## Сегмент

```lua
FastesBoooy.AddSegment("horde-undead-paladin", {
    id = "ud-01-deathknell",
    title = { ru = "1-6 Мертвый Звон", en = "1-6 Deathknell" },
    zone = "Tirisfal Glades",
    levels = { 1, 6 },
    steps = { ... },
})
```

## Шаг

Шаг описывает **одно место / одно действие игрока**. В одном шаге можно
совмещать несколько действий (например, сдать и сразу взять квесты у одного NPC) —
шаг завершён, когда выполнены **все** его действия.

### Действия

| Ключ | Значение | Когда шаг считается выполненным |
|---|---|---|
| `accept` | `id` или `{id, id}` | квест(ы) в журнале или уже сданы |
| `turnin` | `id` или `{id, id}` | квест(ы) сданы (`C_QuestLog.IsQuestFlaggedCompleted`) |
| `complete` | `id`, `{id, id}` или `{ [id] = {1, 2} }` | цели квеста (или указанные цели) выполнены, либо квест сдан |
| `abandon` | `id` или `{id}` | квеста нет в журнале |
| `collect` | `{ [itemId] = count }` | в сумках ≥ count |
| `level` | `n` или `{n, доля}` | уровень > n, или = n и доля опыта ≥ доли |
| `go` | `true` | игрок в радиусе `radius` (по умолч. 12 ярдов) от `at` |
| `train` | `true` | окно тренера было открыто и закрыто на этом шаге (если у шага есть `npc` — окно этого NPC: тренер верховой езды рядом с классовым тренером шаг не завершает) |
| `fp` | `"Brill"` | открыта карта полётов на этом шаге (точка изучена) |
| `fly` | `"Undercity"` | игрок прилетел (не на такси и в радиусе 60 ярдов от `at`) |
| `sethearth` | `"Brill"` | точка привязки камня изменилась на этом шаге или уже равна месту (имя сравнивается и на языке клиента — через `places` из `Data.lua`) |
| `hearth` | `"Brill"` | игрок в радиусе 80 ярдов от `at` после телепорта |
| `vendor` | `true` | окно торговца было открыто и закрыто (с `npc` — окно этого NPC, как у `train`) |
| `manual` | `true` | только вручную (кнопка «дальше») |

`accept/turnin/complete/abandon/collect/level` — **stateful**: их состояние читается
из игры в любой момент. Остальные — **transient**: наблюдаемы только пока шаг
текущий (или в списке «попутно»). Окна тренера и торговца засчитываются шагу, только если
NPC окна (`UnitGUID("npc")`) есть в `npc` шага; шаг без `npc` (или окно, NPC которого клиент
не отдал) засчитывает любое окно этого вида.

**Перемотка вперёд.** Если игрок уже ушёл дальше, пропущенные шаги до «границы
перемотки» считаются выполненными — это позволяет подхватить маршрут на уже
прокачанном персонаже и после пустых SavedVariables. Граница = дальнейшее из:

* **опорный шаг** (anchor) — последний не-`bg` шаг с действием `accept`, `turnin` или
  `complete`, у которого выполнены **все** stateful-действия (или отмеченный вручную).
  Доказательством прогресса **не** служат: `level` (уровень можно набрать раньше —
  rested-опыт, гринд, группа — шаг `{ level = 10 }` сам по себе не перематывает более
  ранние `sethearth`/`train`/`fp`; шаг `{ level = 10, accept = Q }` — опорный, когда
  выполнены оба действия), `abandon` (выполнен «пусто» для никогда не взятого квеста),
  `collect` (предметы могут оказаться в сумках случайно), `bg`-шаги;
* сохранённая отметка самого дальнего достигнутого шага (`FastesBoooyCharDB.cursorHint`).

**Шаг-визит перед квестом того же NPC.** Разговор с NPC сначала открывает его диалог (gossip), и
автоматика сразу берёт квесты маршрута из шагов `[курсор, курсор + lookahead]` (настройка
`lookahead`, по умолчанию 6) и сдаёт выполненные квесты маршрута — **до** того, как игрок откроет
окно тренера, торговца, полётов или привяжет камень. Если за шагом с `train` / `vendor` / `fp` /
`sethearth` у NPC X в пределах 6 шагов идёт шаг, в котором только `accept` квестов X (или `turnin`
уже выполненных квестов X), этот шаг выполняется первым, становится опорным, и визит считается
выполненным (перемотан): курсор уходит дальше, игрок не видит шага «обучиться» / «купить».
Правило: такой визит **не ставят** перед квестами того же NPC в пределах `lookahead`, а
**объединяют** с ними в один шаг (`{ train = true, turnin = A, accept = B, npc = X }` — шаг ждёт
и окно, и квесты) или ставят **после** них. `optional`-визит перематывать можно. Валидатор
сообщает о нарушении `WARN lookahead-skip` (на шаге-визите; там же `-- WARN-OK: причина`), а
симулятор открывает такие визиты через диалог NPC и предупреждает, если визит перемотан.

До границы перематываются: transient-действия, шаги `optional` и два «немонотонных»
stateful-действия, которые иначе вернули бы курсор назад: `collect` (предметы обычно
забирает более поздняя сдача квеста) и `accept` квеста, который **более поздний** шаг
маршрута бросает (`abandon`). Остальные stateful-действия (`accept`, `turnin`,
`complete`, `abandon`, `level`) всегда читаются из игры, даже до границы. `bg`-шаги
границей не перематываются, пока игрок в их сегменте (см. `docs/ARCHITECTURE.md`).

**Квест, от которого игрок отказался.** Порядок действий игрока не важен: можно просто
бросить квест в журнале (таймер истёк, элита не по силам, предмет не выпал), нажимать
«Пропустить» не нужно — ни до, ни после. На `QUEST_REMOVED` (кроме `wasReplayQuest`) гайд
через 0,5 с проверяет, что квест не сдан (`QUEST_TURNED_IN` и `QUEST_REMOVED` приходят и
при сдаче) и не вернулся в журнал. Если шаг с `accept` этого квеста уже позади курсора и до
следующего `accept` того же квеста в маршруте нет явного шага `{ abandon = Q }` (тогда
маршрут сам ведёт квест — его поток не меняется), квест считается **оставленным**:

* невыполненные не-`bg` шаги, все действия которых — `complete`/`turnin` этого квеста,
  отмечаются пропущенными (`FastesBoooyCharDB.skipped`; какие отметки поставил гайд —
  в `FastesBoooyCharDB.gaveUp`), в чат пишется «Задание «X» брошено — его шаги пропущены
  (/fb prev — вернуться)»;
* шаг, где квест смешан с другими действиями (`turnin = { Q, R }`, `turnin = Q, accept = R`),
  не отмечается: действия брошенного квеста в нём считаются выполненными, шаг ждёт только
  остальных;
* `accept` квеста остаётся выполненным: курсор не возвращается к нему, автоматика не берёт
  квест снова; шаги после следующего `accept` того же квеста не трогаются;
* квест, взятый заранее (автоматикой через просмотр вперёд) и брошенный до шага с его
  `accept`, ничего не меняет — до `accept` маршрут ещё дойдёт.

Так же оставленным считается квест, более поздний шаг с `complete`/`turnin` которого отмечен
(«Пропустить» / «Дальше») или является `optional`-шагом позади границы перемотки. Вернуть
брошенный квест: взять его снова вручную (отметки гайда снимаются, шаги квеста снова нужны;
если квест взят для следующего `accept` того же квеста в окне автоматики, прежний экземпляр
остаётся пропущенным), `/fb prev` сразу после сообщения (или «Назад» на один из отмеченных
шагов) — курсор вернётся к его `accept`; `/fb reset` забывает и эти отметки. Отметки живут в
SavedVariables, как «Пропустить»: холодный старт с пустыми SavedVariables восстанавливает
курсор по состоянию игры (квеста нет в журнале → его `accept`).

Поэтому в заметках достаточно «бросьте квест», например: «Таймер истёк — бросьте 853 (гайд
сам пропустит шаги)». Явный шаг `{ abandon = Q }` нужен, только когда маршрут сам требует
бросить квест в определённом месте.

### Поля

| Поле | Тип | Назначение |
|---|---|---|
| `id` | string | стабильный id шага (иначе `<segment>:<n>`) |
| `at` | `{uiMapID, x, y}` | точка на карте Forever (x, y в процентах 0–100) |
| `radius` | number | радиус прибытия в ярдах |
| `npc` | id / список | NPC (валидатор проверяет, что он выдаёт/принимает квест и стоит рядом с `at`) |
| `object` | id / список | игровой объект (аналогично) |
| `note` | string или `{ru=, en=}` | подсказка |
| `reward` | `{ [questId] = индекс }` | какую награду выбирать автоматически |
| `gossip` | number | номер опции диалога для автовыбора |
| `use` | itemId | предмет для кнопки «использовать» (`FastesBoooyItemButton`, `/click FastesBoooyItemButton`): видна, пока шаг текущий (или `bg`-шаг в списке «попутно») и предмет в сумках; в бою не меняется до конца боя |
| `bg` | boolean | фоновая цель: не блокирует, висит в списке «попутно», пока не выполнена |
| `optional` | boolean | можно пропустить: считается выполненным, когда он позади границы перемотки (выполнен более поздний опорный шаг `accept`/`turnin`/`complete`, не просто `level`) |
| `class` / `race` / `faction` | токен или список | фильтр: шаг показывается только подходящим персонажам |
| `spells` | список строк | что выучить у тренера (только отображение) |

### Пример

```lua
steps = {
    { accept = 363, npc = 1568, at = { 1420, 30.2, 71.7 } },
    { turnin = 363, accept = 364, npc = 1569, at = { 1420, 30.8, 66.2 } },
    { complete = 364, bg = true, note = { ru = "Бейте зомби по пути", en = "Kill zombies on the way" } },
    { level = { 4, 0.3 } },
    { train = true, class = "PALADIN", npc = 12345, at = { 1420, 31.1, 66.0 } },
    { go = true, at = { 1420, 59.4, 52.1 }, note = { ru = "Бегите в Брилл", en = "Run to Brill" } },
}
```

## Общие сегменты и вставки

Путь Орды 22-60 почти одинаков для всех классов, поэтому он живёт в одном
**модуле-библиотеке** (сегменты без классовых шагов), а модуль маршрута класса берёт из неё
нужные сегменты и вставляет свои шаги (тренер, классовые квесты) рядом с шагами библиотеки.
Это аддитивное расширение API v1: маршрут без `UseSegments`/`AddInsert` работает как раньше.
Реализация — [`Core/Compose.lua`](../addons/FastesBoooy/Core/Compose.lua) (чистый Lua, общий
для аддона и всех инструментов: валидатор, симулятор и `gen_route_data` собирают маршрут тем
же кодом, что и игра).

### Модуль-библиотека

(Id квестов, NPC и шагов в примерах этого раздела условные; рабочий пример — фикстура в
конце раздела.)

```
addons/FastesBoooy_Horde/
  FastesBoooy_Horde.toc    -- ## Interface: 16001, ## Dependencies: FastesBoooy,
                           -- ## X-FastesBoooy-Module: library
  Data.lua                 -- (генерируется, make routedata) FastesBoooy.AddLibraryData({...})
  Segments/01_h-22-hillsbrad.lua  -- FastesBoooy.AddLibrarySegment({...}) — по файлу на сегмент
```

`## X-FastesBoooy-Module: library` в TOC объявляет модуль библиотекой явно. Инструменты и так
узнают библиотеку по регистрациям (`AddLibrarySegment`/`AddLibraryData` без маршрута), но
заготовке, у которой сегментов ещё нет (файлы сегментов — только комментарии), объявление
нужно: `gen_route_data` пишет для неё пустой `AddLibraryData({ quests = {}, npcs = {} })`,
валидатор показывает её как библиотеку (0 сегментов), симулятор пропускает. Другое значение
поля или маршрут в объявленной библиотеке — ошибка загрузки. Клиент поле не читает (`X-` —
свободные метаданные TOC).

```lua
FastesBoooy.AddLibrarySegment({
    id = "h-22-barrens",                      -- id общих сегментов Орды: префикс "h-" (соглашение)
    title = { ru = "22-24 Степи", en = "22-24 The Barrens" },
    zone = "The Barrens",
    levels = { 22, 24 },
    steps = {                                 -- формат шагов тот же, что у AddSegment
        { id = "h-22-accept-1234", accept = 1234, npc = 3448, at = { 1413, 52.3, 31.9 } },
        { id = "h-22-fp-xroads", fp = "The Crossroads", npc = 3615, at = { 1413, 51.5, 30.3 } },
        ...
    },
})
```

* Библиотека не регистрирует маршрут и не зависит от класса: классовые шаги — во вставках
  модулей маршрутов. Фильтры `class`/`race`/`faction` в шагах библиотеки допустимы, но
  обычно не нужны.
* Id сегментов и id шагов уникальны **во всей библиотеке** (все модули-библиотеки делят одно
  пространство имён): шаги разных сегментов можно комбинировать в одном маршруте. Явные id
  шагов обязательны по смыслу (якоря вставок и `cursorHint` ссылаются на id); по соглашению
  они начинаются с `h-` (Орда). Без id шаг получает `<сегмент>:<n>`, как в `AddSegment`.
* `Data.lua` библиотеки генерирует `make routedata`: `FastesBoooy.AddLibraryData({ quests = {...},
  npcs = {...}, objects = ..., items = ..., places = {...} })` — всё, на что ссылаются её
  сегменты. Эти имена подмешиваются в данные каждого маршрута, который использует сегменты
  библиотеки (значения самого маршрута важнее).

### Маршрут, который использует библиотеку

```
## Dependencies: FastesBoooy, FastesBoooy_Horde     -- в TOC модуля маршрута: библиотека грузится раньше
```

```lua
-- Route.lua
FastesBoooy.RegisterRoute({ api = 1, id = "horde-undead-paladin", levels = { 1, 60 }, ... })
FastesBoooy.UseSegments("horde-undead-paladin", {
    "h-22-barrens", "h-24-stonetalon", "pal-26-class", "h-27-hillsbrad", ...
})

-- Inserts.lua (классовые шаги)
FastesBoooy.AddInsert("horde-undead-paladin", {
    after = "h-24-turnin-1062",               -- id шага маршрута: своего или библиотечного
    steps = {
        { id = "pal-24-train", train = true, class = "PALADIN", npc = 3352, at = { 1454, 45.1, 76.9 } },
    },
})
FastesBoooy.AddInsert("horde-undead-paladin", {
    before = "h-27-accept-498",
    steps = { { id = "pal-26-level", level = 26 } },
})
```

**`FastesBoooy.UseSegments(routeId, { id, ... })`** — добавляет сегменты библиотеки после
собственных сегментов маршрута, в порядке списка (несколько вызовов — в порядке вызовов).
Вызывать **после** `RegisterRoute` (иначе — ошибка регистрации, вызов ставится в очередь, как
`AddSegment` до маршрута). Элемент списка может назвать и **собственный** сегмент маршрута
(`"pal-26-class"` выше): тогда этот сегмент встаёт в это место списка, а не в начало — так
целый классовый сегмент (поездка к тренеру, цепочка классовых квестов) помещается между
общими сегментами. Неизвестный id — ошибка регистрации (один раз): «unknown library segment
… list it in ## Dependencies»; id, указанный дважды, — ошибка (второй пропускается).

**`FastesBoooy.AddInsert(routeId, { after = "<stepId>" | before = "<stepId>", steps = {...} })`** —
вставляет шаги маршрута сразу после / перед шагом-якорем:

* якорь — любой шаг маршрута после сборки: собственный, библиотечный или шаг другой вставки;
  неизвестный якорь — ошибка регистрации (вставка пропускается);
* вставленные шаги принадлежат **сегменту якоря** (заголовок окна, перемотка `bg`-шагов по
  сегментам, отчёт валидатора);
* несколько вставок у одного якоря сохраняют **порядок вызовов** (`after`: A, B → якорь, A, B;
  `before`: A, B → A, B, якорь);
* явные id рекомендуются; без id шаг получает `<id якоря>+<n>` (n — номер шага среди всех
  вставленных у этого якоря, по порядку вызовов);
* формат шагов — как в `AddSegment`; ошибки формата сообщаются сразу при вызове.

Вставки можно регистрировать до или после `UseSegments` (и до/после `AddSegment` своих
сегментов): маршрут **собирается лениво**, когда его впервые читают после изменения
(`PLAYER_LOGIN` — только маршруты, подходящие персонажу; выбор маршрута, окно настроек). Достаточно, чтобы все вызовы прошли во время
загрузки модулей. Если библиотека или маршрут меняются позже (модуль загружен после входа),
маршрут пересобирается.

**Id шагов уникальны в пределах маршрута после сборки** (свои + библиотечные + вставленные);
совпадение — ошибка регистрации («duplicate step id … after composition»), как и в `AddSegment`.

Собранный маршрут для движка ничем не отличается от обычного: фильтры шагов, `bg`, `optional`,
граница перемотки, брошенные квесты, `cursorHint` по id шага, холодный старт — всё работает
одинаково, в том числе на стыках своих, библиотечных и вставленных шагов.

### Пример сборки

```
свои сегменты:      tc-intro { tc-intro-go },  tc-class { tc-train-4 }
библиотека:         tl-deathknell { tl-accept-363, tl-363-364, ..., tl-turnin-3901, tl-turnin-376 }
                    tl-brill { ..., tl-sethearth }
UseSegments:        { "tl-deathknell", "tc-class", "tl-brill" }
AddInsert:          after "tl-363-364" { tc-train-1 };  after "tl-363-364" { tc-vendor-1 }
                    before "tl-turnin-3901" { (без id) };  before "tc-intro-go" { tc-welcome }

результат:          tc-intro:      tc-welcome, tc-intro-go
                    tl-deathknell: tl-accept-363, tl-363-364, tc-train-1, tc-vendor-1, ...,
                                   tl-turnin-3901+1, tl-turnin-3901, tl-turnin-376
                    tc-class:      tc-train-4
                    tl-brill:      ..., tl-sethearth
```

(Это фикстура тестов `tests/fixtures/core/FastesBoooy_TestLib` + `FastesBoooy_TestComposed`.)

### Версия ядра

`UseSegments`, `AddInsert`, `AddLibrarySegment` и `AddLibraryData` есть в ядре начиная с
**0.2.0**. Формат маршрутов остаётся `api = 1` (расширение аддитивное), а уровень возможностей
ядра виден в `FastesBoooy.API_MINOR`: `1` — ядро 0.2.0 с библиотеками и вставками; у ядра 0.1.x
поля нет. Со старым ядром модуль маршрута, вызвавший `UseSegments`, получил бы ошибку Lua
(`attempt to call field 'UseSegments' (a nil value)`), поэтому модули библиотек и маршрутов
могут проверить версию в первом файле TOC и выйти с понятным сообщением:

```lua
-- Data.lua (библиотека) / Route.lua (маршрут): первая строка модуля
if (FastesBoooy.API_MINOR or 0) < 1 then
    print("FastesBoooy_Horde: обновите аддон FastesBoooy (нужно ядро 0.2.0+) / update the FastesBoooy core (0.2.0+)")
    return
end
```

(`return` прекращает только этот файл; остальные файлы модуля тогда тоже должны проверять
`FastesBoooy.UseSegments` / `FastesBoooy.AddLibrarySegment` перед вызовом или полагаться на то,
что без зарегистрированного маршрута их вызовы ничего не ломают.) `/fb status` показывает версию
ядра и `route API 1.1`.

### Данные и инструменты

* `Data.lua` модуля маршрута (`make routedata`) перечисляет только то, на что ссылаются его
  **собственные сегменты и вставки**; имена библиотечных шагов приходят из `Data.lua`
  библиотеки (`AddLibraryData`).
* Валидатор, симулятор и `gen_route_data` читают `## Dependencies` / `## RequiredDeps` TOC
  модуля и загружают модули `FastesBoooy_*` из того же каталога раньше него (в песочнице, как
  клиент), затем собирают маршрут кодом `Core/Compose.lua`. Сообщения валидатора о шагах
  библиотеки помечены `[library FastesBoooy_Horde]` (файл — `FastesBoooy_Horde/Segments/…`) и
  выводятся один раз на маршрут; ошибки загрузки самой библиотеки — один раз за запуск.
  Симулятор проигрывает только модули маршрутов (библиотека загружается как зависимость).
* luacheck проверяет модули-библиотеки тем же std, что и модули маршрутов (только API
  `FastesBoooy.*`).
* **Часть библиотеки из стартового состояния** (сегменты пишутся параллельно): валидатор и
  симулятор с `--harness <каталог библиотеки> --segments h-a,h-b --profile race=…,class=…,faction=…
  --state <состояние.json> [--write-state <конец.json>]` собирают синтетический маршрут
  (`RegisterRoute` для одного профиля + `UseSegments` перечисленных сегментов, ничего больше) и
  проверяют / проигрывают его, начиная с уровня, сданных квестов, журнала, камня и точек полёта
  из файла состояния. `--write-state` пишет состояние в конце (тот же формат — звенья цепочки);
  у полного маршрута тоже: `validate_routes.lua --route <id> --write-state f.json`. Подробно —
  [tools/README.md](../tools/README.md), раздел «Harness».

## Валидация

`make validate` (см. `tools/validate_routes.lua`) проверяет каждый маршрут по
снимку базы Forever (`tools/data/forever_db.lua`): существование квестов,
доступность для расы/класса/фракции, требования по уровню (симуляция опыта),
цепочки (pre-quests, exclusive), принадлежность NPC и расстояние от `at` до
спавна, ёмкость журнала, тренеров/полётчиков/трактирщиков. Подробнее —
[VALIDATION.md](VALIDATION.md).
