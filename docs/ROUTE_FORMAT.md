# Формат маршрутов (API v1)

Маршрут — это обычный аддон-модуль, который зависит от ядра `AdventureAtlas` и
регистрирует данные через глобальную таблицу `AdventureAtlas`. Контракт формата
реализован в [`addons/AdventureAtlas/Core/Schema.lua`](../addons/AdventureAtlas/Core/Schema.lua)
(чистый Lua 5.1, общий для аддона и офлайн-валидатора).

## Структура модуля

```
addons/AdventureAtlas_<Name>/
  AdventureAtlas_<Name>.toc  -- ## Interface: 16001, ## Dependencies: AdventureAtlas
  Route.lua                  -- AdventureAtlas.RegisterRoute{...}
  Data.lua                   -- (генерируется, make routedata) AdventureAtlas.AddRouteData(id, {quests=..., npcs=..., places=...,
                             --   questMeta=...})
  Segments/01_*.lua          -- AdventureAtlas.AddSegment(id, {...}) — по файлу на сегмент
```

Файлы грузятся в порядке TOC. `RegisterRoute` должен идти первым.

Маршрут может брать готовые **общие сегменты** (например, общий путь 12-60 модуля
`AdventureAtlas_Guides`, `Segments/Shared/`) и добавлять к ним свои классовые шаги — см. раздел
[«Общие сегменты и вставки»](#общие-сегменты-и-вставки). Один модуль может держать и общие
сегменты, и общие вставки классов и рас, и сразу много маршрутов (так устроен
`AdventureAtlas_Guides`: 28 маршрутов «раса + класс» из одного набора файлов) — см.
[«Общие вставки»](#общие-вставки-addlibraryinsert) и
[«Модуль с общим содержимым и маршрутами»](#модуль-с-общим-содержимым-и-маршрутами).

## Маршрут

```lua
AdventureAtlas.RegisterRoute({
    api = 1,                                  -- версия формата (обязательно)
    id = "undead-paladin",                    -- [A-Za-z0-9-_]
    title = { ru = "Нежить-паладин 1-60", en = "Undead Paladin 1-60" },
    faction = "Horde",                        -- "Horde" | "Alliance"
    races = { "Scourge" },                    -- raceFile из UnitRace()
    classes = { "PALADIN" },                  -- classFile из UnitClass()
    levels = { 1, 60 },                       -- {от, до}, до 60 (капа уровня Forever)
    version = "1.0.0",
    default = true,                           -- автоматически выбирать для подходящих персонажей
    aliases = { "horde-undead-paladin" },     -- прежние id маршрута (строка или список), см. ниже
})
```

### Переименование маршрута: `aliases`

`aliases = "старый-id"` или `{ "старый-id", ... }` — id, под которыми маршрут был известен
раньше (ядро 0.4.0+). Сохранённый прогресс персонажа привязан к id маршрута; алиас переносит
его на новый id:

* `Registry:Get(id)` (и `/aa route <id>`) находит маршрут и по алиасу, если маршрута с таким
  id нет — **id маршрута всегда важнее алиаса**;
* при активации маршрута (`Engine:ActivateRoute`) записи `AdventureAtlasCharDB.route`,
  `cursorHintRoute`, `syncFloor.route` и `syncDismissed.route`, которые хранят алиас,
  переписываются на новый id: выбранный вручную маршрут, отметка самого дальнего шага и порог
  синхронизации переживают переименование. Отметки шагов (`manual`, `skipped`) хранятся по id
  шага и переживают его, пока id шага не изменился;
* ошибки регистрации (алиас игнорируется, маршрут регистрируется): алиас равен id уже
  зарегистрированного маршрута («alias '…' is the id of a registered route»); алиас уже занят
  другим маршрутом («alias '…' is already used by route …»); позже регистрируется маршрут, id
  которого кто-то объявил алиасом («its id is an alias of route …» — старый модуль ещё
  установлен: его маршрут остаётся собой).

Пример: `undead-paladin` модуля `AdventureAtlas_Guides` с `aliases = "horde-undead-paladin"`
принимает прежний id версии 0.3 (`/aa route horde-undead-paladin`; так же `skyborne-druid` ←
`horde-skyborne-druid`). В 0.4 алиас переносил и прогресс, начатый в модуле `FastesBoooy_UndeadPaladin`;
сохранённые данные аддона под прежним именем FastesBoooy в Adventure Atlas не переносятся (README,
«Обновление с FastesBoooy»).

## Сегмент

Собственный сегмент маршрута (`AddSegment`; у маршрутов `AdventureAtlas_Guides` своих сегментов
нет — тот же формат там регистрирует `AddLibrarySegment`, см. «Общие сегменты и вставки»):

```lua
AdventureAtlas.AddSegment("my-route", {
    id = "ud-01-deathknell",
    title = { ru = "1-6 Мертвый Звон", en = "1-6 Deathknell" },
    zone = "Tirisfal Glades",
    levels = { 1, 6 },
    steps = { ... },
    ok = "segment-level",                     -- необязательно: принятое предупреждение о сегменте, см. `ok`
})
```

**`levels` сегмента — не только подпись: держите его точным** (план уровня игрока на этом участке:
`{ уровень в начале, уровень в конце }`). Движок использует его:

* **синхронизация по уровню**: сегмент «перерос по уровню», если `уровень игрока ≥ levels[2] +
  запас` (настройка `levelSyncMargin`, по умолчанию 2); если перерос сегмент текущего шага,
  игроку предлагается первый более поздний сегмент, который он не перерос (баннер окна шагов,
  `/aa sync`, режим `"auto"` — сразу). Слишком низкий `levels[2]` будет уводить игроков вперёд
  раньше времени, слишком высокий — держать их в серой зоне;
* **серые квесты** (`skipGray`): `accept` серого для игрока квеста пропускается, только если
  игрок перерос сегмент этого шага (`уровень > levels[2]`) — серые квесты, которые маршрут берёт
  нарочно на запланированном уровне, остаются;
* `title` сегмента показывается в баннере и в строке чата синхронизации.

Сегмент без `levels` никогда не считается перерощенным и не предлагается как цель
синхронизации.

## Шаг

Шаг описывает **одно место / одно действие игрока**. В одном шаге можно
совмещать несколько действий (например, сдать и сразу взять квесты у одного NPC) —
шаг завершён, когда выполнены **все** его действия.

### Действия

| Ключ | Значение | Когда шаг считается выполненным |
|---|---|---|
| `accept` | `id` или `{id, id}` | квест(ы) в журнале или уже сданы |
| `turnin` | `id` или `{id, id}` | квест(ы) сданы (`C_QuestLog.IsQuestFlaggedCompleted`) |
| `complete` | `id`, `{id, id}` или `{ [id] = {1, 2} }` | цели квеста (или указанные цели) выполнены, либо квест сдан |
| `abandon` | `id` или `{id}` | квеста нет в журнале |
| `collect` | `{ [itemId] = count }` | в сумках ≥ count |
| `level` | `n` или `{n, доля}` | уровень > n, или = n и доля опыта ≥ доли |
| `go` | `true` | игрок в радиусе `radius` (по умолч. 12 ярдов) от `at` |
| `train` | `true` | окно тренера было открыто и закрыто на этом шаге (если у шага есть `npc` — окно этого NPC: тренер верховой езды рядом с классовым тренером шаг не завершает) |
| `fp` | `"Brill"` | открыта карта полётов на этом шаге (точка изучена): у NPC из `npc` либо рядом с `at` (карта другого распорядителя полётов не засчитывается; без `npc` и `at` — любая) |
| `fly` | `"Undercity"` | игрок прилетел (не на такси и в радиусе 60 ярдов от `at`) |
| `sethearth` | `"Brill"` | точка привязки камня изменилась на этом шаге или уже равна месту (имя сравнивается и на языке клиента — через `places` из `Data.lua`) |
| `hearth` | `"Brill"` | игрок в радиусе 80 ярдов от `at` после телепорта |
| `vendor` | `true` | окно торговца было открыто и закрыто (с `npc` — окно этого NPC, как у `train`) |
| `manual` | `true` | только вручную (кнопка «Вперёд», `/aa next`) |

`accept/turnin/complete/abandon/collect/level` — **stateful**: их состояние читается
из игры в любой момент. Остальные — **transient**: наблюдаемы только пока шаг
текущий (или в списке «попутно»). Окна тренера и торговца засчитываются шагу, только если
NPC окна (`UnitGUID("npc")`) есть в `npc` шага; шаг без `npc` (или окно, NPC которого клиент
не отдал) засчитывает любое окно этого вида.

**Перемотка вперёд.** Если игрок уже ушёл дальше, пропущенные шаги до «границы
перемотки» считаются выполненными — это позволяет подхватить маршрут на уже
прокачанном персонаже и после пустых SavedVariables. Граница = дальнейшее из:

* **опорный шаг** (anchor) — последний не-`bg` шаг с действием `accept`, `turnin` или
  `complete`, у которого выполнены **все** stateful-действия (или отмеченный вручную).
  Доказательством прогресса **не** служат: `level` (уровень можно набрать раньше —
  rested-опыт, гринд, группа — шаг `{ level = 10 }` сам по себе не перематывает более
  ранние `sethearth`/`train`/`fp`; шаг `{ level = 10, accept = Q }` — опорный, когда
  выполнены оба действия), `abandon` (выполнен «пусто» для никогда не взятого квеста),
  `collect` (предметы могут оказаться в сумках случайно), `bg`-шаги;
* сохранённая отметка самого дальнего достигнутого шага (`AdventureAtlasCharDB.cursorHint`).

**Шаг-визит перед квестом того же NPC.** Разговор с NPC сначала открывает его диалог (gossip), и
автоматика сразу берёт квесты маршрута из шагов `[курсор, курсор + lookahead]` (настройка
`lookahead`, по умолчанию 6) и сдаёт выполненные квесты маршрута — **до** того, как игрок откроет
окно тренера, торговца, полётов или привяжет камень. Если за шагом с `train` / `vendor` / `fp` /
`sethearth` у NPC X в пределах 6 шагов идёт шаг, в котором только `accept` квестов X (или `turnin`
уже выполненных квестов X), этот шаг выполняется первым, становится опорным, и визит считается
выполненным (перемотан): курсор уходит дальше, игрок не видит шага «обучиться» / «купить».
Правило: такой визит **не ставят** перед квестами того же NPC в пределах `lookahead`, а
**объединяют** с ними в один шаг (`{ train = true, turnin = A, accept = B, npc = X }` — шаг ждёт
и окно, и квесты) или ставят **после** них. `optional`-визит перематывать можно. Валидатор
сообщает о нарушении `WARN lookahead-skip` (на шаге-визите; принять его можно там же:
`ok = "lookahead-skip"` и причина в комментарии), а
симулятор открывает такие визиты через диалог NPC и предупреждает, если визит перемотан.

До границы перематываются: transient-действия, шаги `optional` и два «немонотонных»
stateful-действия, которые иначе вернули бы курсор назад: `collect` (предметы обычно
забирает более поздняя сдача квеста) и `accept` квеста, который **более поздний** шаг
маршрута бросает (`abandon`). Остальные stateful-действия (`accept`, `turnin`,
`complete`, `abandon`, `level`) всегда читаются из игры, даже до границы. `bg`-шаги
границей не перематываются, пока игрок в их сегменте (см. `docs/ARCHITECTURE.md`).

**Квест, от которого игрок отказался.** Порядок действий игрока не важен: можно просто
бросить квест в журнале (таймер истёк, элита не по силам, предмет не выпал), нажимать
«Пропустить» не нужно — ни до, ни после. На `QUEST_REMOVED` (кроме `wasReplayQuest`) гайд
через 0,5 с проверяет, что квест не сдан (`QUEST_TURNED_IN` и `QUEST_REMOVED` приходят и
при сдаче) и не вернулся в журнал. Если шаг с `accept` этого квеста уже позади курсора и до
следующего `accept` того же квеста в маршруте нет явного шага `{ abandon = Q }` (тогда
маршрут сам ведёт квест — его поток не меняется), квест считается **оставленным**:

* невыполненные не-`bg` шаги, все действия которых — `complete`/`turnin` этого квеста,
  отмечаются пропущенными (`AdventureAtlasCharDB.skipped`; какие отметки поставил гайд —
  в `AdventureAtlasCharDB.gaveUp`), в чат пишется «Задание «X» брошено — его шаги пропущены
  (/aa prev — вернуться)»;
* шаг, где квест смешан с другими действиями (`turnin = { Q, R }`, `turnin = Q, accept = R`),
  не отмечается: действия брошенного квеста в нём считаются выполненными, шаг ждёт только
  остальных;
* `accept` квеста остаётся выполненным: курсор не возвращается к нему, автоматика не берёт
  квест снова; шаги после следующего `accept` того же квеста не трогаются;
* квест, взятый заранее (автоматикой через просмотр вперёд) и брошенный до шага с его
  `accept`, ничего не меняет — до `accept` маршрут ещё дойдёт.

Так же оставленным считается квест, более поздний шаг с `complete`/`turnin` которого отмечен
(кнопкой «Вперёд», `/aa skip` / `/aa next`) или является `optional`-шагом позади границы перемотки. Вернуть
брошенный квест: взять его снова вручную (отметки гайда снимаются, шаги квеста снова нужны;
если квест взят для следующего `accept` того же квеста в окне автоматики, прежний экземпляр
остаётся пропущенным), `/aa prev` сразу после сообщения (или «Назад» на один из отмеченных
шагов) — курсор вернётся к его `accept`; `/aa reset` забывает и эти отметки. Отметки живут в
SavedVariables, как пропуск шага: холодный старт с пустыми SavedVariables восстанавливает
курсор по состоянию игры (квеста нет в журнале → его `accept`).

Поэтому в заметках достаточно «бросьте квест», например: «Таймер истёк — бросьте 853 (гайд
сам пропустит шаги)». Явный шаг `{ abandon = Q }` нужен, только когда маршрут сам требует
бросить квест в определённом месте.

### Поля

| Поле | Тип | Назначение |
|---|---|---|
| `id` | string | стабильный id шага (иначе `<segment>:<n>`) |
| `at` | `{uiMapID, x, y}` | точка на карте Forever (x, y в процентах 0–100) |
| `radius` | number | радиус прибытия в ярдах |
| `npc` | id / список | NPC (валидатор проверяет, что он выдаёт/принимает квест и стоит рядом с `at`) |
| `object` | id / список | игровой объект (аналогично) |
| `note` | string или `{ru=, en=}` | подсказка |
| `reward` | `{ [questId] = индекс }` | какую награду выбирать автоматически. Для квеста, который сдаётся на общем шаге, выбор по классу задаёт [таблица наград](#таблица-наград-по-классам); `reward` шага важнее таблицы |
| `gossip` | number | номер опции диалога для автовыбора |
| `use` | itemId | предмет, который используют на шаге. Ядро его не показывает (своей кнопки предмета нет: игрок пользуется кнопкой интерфейса игры в списке заданий); поле проверяется и сохраняется для данных маршрута |
| `bg` | boolean | фоновая цель: не блокирует, висит в списке «попутно», пока не выполнена |
| `optional` | boolean | можно пропустить: считается выполненным, когда он позади границы перемотки (выполнен более поздний опорный шаг `accept`/`turnin`/`complete`, не просто `level`) |
| `class` / `race` / `faction` | токен или список | фильтр: шаг показывается только подходящим персонажам. Раса — `raceFile` из `UnitRace()` (`"Scourge"`, не `"Undead"`). Общий шаг, фильтр которого не может совпасть с маршрутом, в этот маршрут не попадает вовсе (см. «Общие сегменты и вставки») |
| `spells` | список строк | что выучить у тренера (только отображение) |
| `ok` | код, список кодов или `{ [код] = число }` | принятые предупреждения валидатора для этого шага (движок поле не читает), см. ниже |

### Принятые предупреждения: `ok`

Валидатор (`make validate`) сообщает о вероятных проблемах как `WARN`. Если автор проверил
предупреждение и оставляет шаг как есть, он **принимает** его ключом `ok` на том же шаге (для
сообщения о сегменте — `segment-level` — на сегменте) и пишет причину комментарием в той же
строке:

```lua
{ id = "ud02-letter", accept = 361, at = { 1420, 58.2, 51.4 }, ok = "at-far-from-giver" },  -- письмо в сумке
{ turnin = 1098, at = { 1421, 44.0, 40.9 }, ok = { "at-far-from-giver", "quest-out-of-scope" } },
{ id = "h39-level-mannoroc", level = { 39, 0.78 }, ok = { ["level-grind"] = 700 } },        -- квестов до 40 нет
{ level = 30, ok = { "skip-ahead", ["level-grind"] = 90 } },
```

(Id в примерах условные.)

* Три формы: код, список кодов, таблица — в ней можно смешивать коды и пары `[код] = число`.
  Код — код сообщения валидатора (`[a-z-]+`, список — в [tools/README.md](../tools/README.md)).
  Схема проверяет только форму; ядро и движок ключ игнорируют.
* Принятое предупреждение не печатается без `-v`, считается отдельно («W warning(s), A accepted»)
  и не роняет `--strict`. Принять можно только `WARN`: `ERROR` исправляют.
* **Потолок.** `[код] = N` принимает предупреждение, только пока число убийств в нём не больше
  `N`; выше — это снова `WARN` («above the acknowledged ceiling»). `level-grind` (гринд до порога
  уровня) принимается **только с потолком**: `ok = "level-grind"` без числа — `ERROR
  ok-needs-ceiling`. Порог на общем шаге проходят все маршруты, и принятый без числа он пропустил
  бы любой гринд у любого класса.
* Устаревшая запись — `WARN ok-unused`: код в `ok`, о котором валидатор на этом шаге не
  сообщает ни в одном маршруте (проверяется на полном запуске).
* `ok` ставится на шаг, который назван в сообщении (`quest-carried` — на шаге с `accept`).
* Прежние комментарии `-- WARN-OK: причина` валидатор не читает; при переносе шага в новый
  модуль они заменяются ключом `ok`.
* Шаг, который проходит проверку только благодаря непроверенной поправке к БД
  (`tools/overrides`, `verified = false`), получает `WARN db-override-unverified`; его принимают
  `ok = "db-override-unverified"` и комментарием `-- CONFIRM: что проверить в игре`. Такие шаги
  перечислены в конце [VALIDATION.md](VALIDATION.md).

### Пример

```lua
steps = {
    { accept = 363, npc = 1568, at = { 1420, 30.2, 71.7 } },
    { turnin = 363, accept = 364, npc = 1569, at = { 1420, 30.8, 66.2 } },
```

## Общие сегменты и вставки

Путь Орды 22-60 почти одинаков для всех классов, поэтому он живёт в одном
**модуле-библиотеке** (сегменты без классовых шагов), а модуль маршрута класса берёт из неё
нужные сегменты и вставляет свои шаги (тренер, классовые квесты) рядом с шагами библиотеки.
Это аддитивное расширение API v1: маршрут без `UseSegments`/`AddInsert` работает как раньше.
Реализация — [`Core/Compose.lua`](../addons/AdventureAtlas/Core/Compose.lua) (чистый Lua, общий
для аддона и всех инструментов: валидатор, симулятор и `gen_route_data` собирают маршрут тем
же кодом, что и игра).

### Модуль-библиотека

(Id квестов, NPC и шагов в примерах этого раздела условные; рабочий пример — фикстура в
конце раздела. Отдельный модуль-библиотека нужен, когда общее содержимое делят несколько
аддонов; так был устроен общий путь 22-60 до версии 0.4 (`FastesBoooy_Horde`). Модуль гайдов
`AdventureAtlas_Guides` регистрирует общее содержимое и маршруты сам — см. [«Модуль с общим
содержимым и маршрутами»](#модуль-с-общим-содержимым-и-маршрутами).)

```
addons/AdventureAtlas_MyLib/
  AdventureAtlas_MyLib.toc  -- ## Interface: 16001, ## Dependencies: AdventureAtlas,
                            -- ## X-AdventureAtlas-Module: library
  Data.lua                  -- (генерируется, make routedata) AdventureAtlas.AddLibraryData({...})
  Segments/01_h-22-hillsbrad.lua  -- AdventureAtlas.AddLibrarySegment({...}) — по файлу на сегмент
```

`## X-AdventureAtlas-Module: library` в TOC объявляет модуль библиотекой явно. Инструменты и так
узнают библиотеку по регистрациям (`AddLibrarySegment`/`AddLibraryData` без маршрута), но
заготовке, у которой сегментов ещё нет (файлы сегментов — только комментарии), объявление
нужно: `gen_route_data` пишет для неё пустой `AddLibraryData({ quests = {}, npcs = {} })`,
валидатор показывает её как библиотеку (0 сегментов), симулятор пропускает. Значение `data` носят
аддоны данных атласа без маршрутов (`AdventureAtlas_Knowledge`): инструменты маршрутов их не ищут и не
проверяют. Другое значение поля (или `data` у каталога, переданного инструменту явно) и маршрут в объявленной
библиотеке — ошибка загрузки. Клиент поле не читает (`X-` —
свободные метаданные TOC).

```lua
AdventureAtlas.AddLibrarySegment({
    id = "h-22-barrens",                      -- id общих сегментов пути: префикс "h-" (соглашение)
    title = { ru = "22-24 Степи", en = "22-24 The Barrens" },
    zone = "The Barrens",
    levels = { 22, 24 },
    steps = {                                 -- формат шагов тот же, что у AddSegment
        { id = "h-22-accept-1234", accept = 1234, npc = 3448, at = { 1413, 52.3, 31.9 } },
        { id = "h-22-fp-xroads", fp = "The Crossroads", npc = 3615, at = { 1413, 51.5, 30.3 } },
        ...
    },
})
```

* Библиотека не регистрирует маршрут и не зависит от класса: классовые шаги — во вставках
  (`AddInsert` модуля маршрута или общие вставки `AddLibraryInsert`, ниже).
* **Фильтры в общих шагах.** `class`/`race`/`faction` в шаге общего сегмента допустимы. Общий шаг,
  фильтр которого **не может совпасть с маршрутом** (не пересекается с `classes`, `races` или
  `faction` маршрута), в этот маршрут **не попадает** (ядро 0.4.0+): его нет среди шагов
  маршрута, он не может быть якорем вставки в этом маршруте, а вставка `AddInsert` на такой якорь
  получит ошибку «unknown anchor step». Так пара шагов-альтернатив с фильтрами по расе (`race =
  "Orc"` / `race = "Troll"`) даёт каждому маршруту свою половину. Позиционные id остальных шагов
  (`<сегмент>:<n>`) от этого не меняются: id назначаются при `AddLibrarySegment`. Маршрут без
  `classes` / `races` получает все шаги, и фильтрует их движок по персонажу, как раньше. Общий
  сегмент, ни один шаг которого маршруту не подходит, в маршрут не попадает совсем.
* Id сегментов и id шагов уникальны **во всей библиотеке** (все модули-библиотеки делят одно
  пространство имён): шаги разных сегментов можно комбинировать в одном маршруте. Явные id
  шагов обязательны по смыслу (якоря вставок и `cursorHint` ссылаются на id); по соглашению
  шаги общего пути начинаются с `h` (`h-22-…`, `h15-…`), шаги стартовых зон — с префикса зоны
  (`ud01-…`, `sd02-…`). Без id шаг получает `<сегмент>:<n>`, как в `AddSegment`.
* `Data.lua` библиотеки генерирует `make routedata`: `AdventureAtlas.AddLibraryData({ quests = {...},
  npcs = {...}, objects = ..., items = ..., places = {...}, questMeta = {...} })` — всё, на что
  ссылаются её сегменты. Эти данные подмешиваются в данные каждого маршрута, который использует
  сегменты библиотеки (значения самого маршрута важнее; `questMeta` — по квесту).

### Маршрут, который использует библиотеку

```
## Dependencies: AdventureAtlas, AdventureAtlas_MyLib  -- в TOC модуля маршрута: библиотека грузится раньше
```

```lua
-- Route.lua
AdventureAtlas.RegisterRoute({ api = 1, id = "my-route", levels = { 1, 60 }, ... })
AdventureAtlas.UseSegments("my-route", {
    "h-22-barrens", "h-24-stonetalon", "pal-26-class", "h-27-hillsbrad", ...
})

-- Inserts.lua (классовые шаги)
AdventureAtlas.AddInsert("my-route", {
    after = "h-24-turnin-1062",               -- id шага маршрута: своего или библиотечного
    steps = {
        { id = "pal-24-train", train = true, class = "PALADIN", npc = 3352, at = { 1454, 45.1, 76.9 } },
    },
})
AdventureAtlas.AddInsert("my-route", {
    before = "h-27-accept-498",
    steps = { { id = "pal-26-level", level = 26 } },
})
```

**`AdventureAtlas.UseSegments(routeId, { id, ... })`** — добавляет сегменты библиотеки после
собственных сегментов маршрута, в порядке списка (несколько вызовов — в порядке вызовов).
Вызывать **после** `RegisterRoute` (иначе — ошибка регистрации, вызов ставится в очередь, как
`AddSegment` до маршрута). Элемент списка может назвать и **собственный** сегмент маршрута
(`"pal-26-class"` выше): тогда этот сегмент встаёт в это место списка, а не в начало — так
целый классовый сегмент (поездка к тренеру, цепочка классовых квестов) помещается между
общими сегментами. Неизвестный id — ошибка регистрации (один раз): «unknown library segment
… list it in ## Dependencies»; id, указанный дважды, — ошибка (второй пропускается).

**`AdventureAtlas.AddInsert(routeId, { after = "<stepId>" | before = "<stepId>", steps = {...} })`** —
вставляет шаги маршрута сразу после / перед шагом-якорем:

* якорь — любой шаг маршрута после сборки: собственный, библиотечный или шаг другой вставки;
  неизвестный якорь — ошибка регистрации (вставка пропускается);
* вставленные шаги принадлежат **сегменту якоря** (заголовок окна, перемотка `bg`-шагов по
  сегментам, отчёт валидатора);
* несколько вставок у одного якоря сохраняют **порядок вызовов** (`after`: A, B → якорь, A, B;
  `before`: A, B → A, B, якорь);
* явные id рекомендуются; без id шаг получает `<id якоря>+<n>` (n — номер шага среди всех
  вставленных у этого якоря, по порядку вызовов);
* формат шагов — как в `AddSegment`; ошибки формата сообщаются сразу при вызове.

Вставки можно регистрировать до или после `UseSegments` (и до/после `AddSegment` своих
сегментов): маршрут **собирается лениво**, когда его впервые читают после изменения
(`PLAYER_LOGIN` — только маршруты, подходящие персонажу; выбор маршрута, окно настроек). Достаточно, чтобы все вызовы прошли во время
загрузки модулей. Если библиотека или маршрут меняются позже (модуль загружен после входа),
маршрут пересобирается.

**Id шагов уникальны в пределах маршрута после сборки** (свои + библиотечные + вставленные);
совпадение — ошибка регистрации («duplicate step id … after composition»), как и в `AddSegment`.

Собранный маршрут для движка ничем не отличается от обычного: фильтры шагов, `bg`, `optional`,
граница перемотки, брошенные квесты, `cursorHint` по id шага, холодный старт — всё работает
одинаково, в том числе на стыках своих, библиотечных и вставленных шагов.

### Общие вставки: `AddLibraryInsert`

Вставка `AddInsert` принадлежит одному маршруту. Когда маршрутов много (каждый класс — у
нескольких рас, каждая раса — с несколькими классами), шаги класса и расы регистрируются **один
раз** как общие вставки (ядро 0.4.0+) и попадают во все маршруты, которым подходят:

```lua
AdventureAtlas.AddLibraryInsert({
    after = "h15-xroads-fp",       -- или before = "<stepId>": ровно одно из двух
    class = "WARRIOR",             -- область: токен или список токенов класса (необязательно)
    race = { "Orc", "Troll" },     -- область: raceFile или список (необязательно)
    faction = "Horde",             -- область (необязательно)
    steps = {                      -- непустой список; формат шагов тот же
        { id = "war-train-16", train = true, npc = 3354, at = { 1454, 79.9, 31.4 } },
    },
})
```

(Id и координаты условные.)

1. **Где применяется.** В каждом маршруте с `UseSegments`, среди собранных шагов которого есть
   якорь. Маршрут без якоря — не ошибка для ядра (ошибки автора ловят инструменты, см. ниже).
   Маршруты без `UseSegments` не затрагиваются.
2. **Область.** `class` / `race` / `faction` вставки — фильтры её шагов по умолчанию; ключ самого
   шага заменяет ключ вставки для этого шага. Шаг, фильтры которого не могут совпасть с маршрутом,
   в этот маршрут не попадает (то же правило, что для шагов общих сегментов). Маршрут без
   `classes` / `races` получает шаг, и его фильтрует движок.
3. **Id.** У каждого шага общей вставки — явный `id`, уникальный среди шагов всех общих сегментов
   и общих вставок (одно пространство имён). Вставка с шагом без id или с повторным id
   отклоняется **целиком**.
4. **Порядок.** В каждом маршруте сначала применяются общие вставки в порядке регистрации (порядок
   файлов в TOC, затем порядок вызовов), потом вставки самого маршрута (`AddInsert`) в порядке
   вызовов. У одного якоря порядок тот же: `after`: A, B → якорь, A, B. Общие шаги не сдвигают
   счётчик `<якорь>+<n>` у шагов `AddInsert` без id. Вставку можно зарегистрировать и раньше той,
   чей шаг служит ей якорем: она применяется, как только якорь появился, раньше всех вставок,
   зарегистрированных после неё, — порядок у якоря остаётся порядком регистрации.
5. **Якорь** — шаг общего сегмента или другой общей вставки (в конкретном маршруте — и его
   собственный шаг) **с явным id**. Позиционный id (`<сегмент>:<n>`) сдвигается при любой правке
   сегмента; вставка на такой якорь применяется, но даёт ошибку сборки «anchor '…' is a positional
   step id: give the anchor step an explicit id».
6. **Копии.** Каждый маршрут получает свои копии шагов вставки (как и шагов общих сегментов);
   шаблоны не меняются. Вставленные шаги принадлежат сегменту якоря.
7. **Метки копий** (их читают инструменты): `inserted`, `shared`, `library = "<модуль>"`, `file`,
   `anchor`, `insertSide`. В отчётах валидатора сообщения о таких шагах — «собственные» сообщения
   маршрута (шаги класса и расы), в отличие от шагов общих сегментов.
8. **Известная особенность порядка.** Вставка, якорь которой — *последний шаг более ранней
   вставки у якоря X*, встаёт после более поздних вставок у X (их место — «после хвоста X»). Не
   полагайтесь на этот порядок: ставьте вставку на X или на шаг общего сегмента.
9. **Общие шаги с фильтром отсекаются по маршруту.** Шаг общего сегмента, фильтр которого не может
   совпасть с маршрутом, в маршрут не попадает (см. «Фильтры в общих шагах» выше). Поэтому шаг с
   фильтром — якорь только в маршрутах своих рас / классов, и вставка на него попадает только
   туда; предупреждение `step-no-profile` для общих шагов больше не возникает (его заменяет
   проверка шаблонов `shared-step-unused`).
10. **Вставка не бывает шире якоря с фильтром.** Если у якоря есть фильтр, каждый шаг вставки должен
    нести область (свою или вставки), которая в каждом отфильтрованном измерении является
    подмножеством фильтра якоря (`race = "Scourge"` у вставки после шага с `race = "Scourge"`).
    Ядру это не нужно (правило 9 и так не пускает вставку в другие маршруты); валидатор требует
    этого (`ERROR insert-scope-wider-than-anchor`), чтобы намерение автора было записано.

Ошибки (в игре — `Registry.errors` с префиксом `library:`, их печатает `/aa routes`; в
инструментах — `schema` с именем файла):

| Ситуация | Когда сообщается |
|---|---|
| не таблица; `after` и `before` вместе или ни одного; якорь — не непустая строка; неизвестный ключ; пустой `steps`; ошибка формата шага; неизвестный токен класса; неверная фракция | при вызове, один раз |
| шаг без `id`; `id`, который уже есть у шага общего сегмента или другой общей вставки; пустой список области (`class = {}`, `race = {}`: без отклонения вставка попала бы во все маршруты) | при вызове, один раз; вставка отклоняется целиком |
| общий сегмент, зарегистрированный позже, повторяет id шага общей вставки | при этом `AddLibrarySegment` («duplicate step id») |
| якоря нет в маршруте | в ядре никогда не ошибка |
| позиционный якорь | при сборке, один раз на маршрут |
| id совпал с собственным шагом маршрута или шагом его `AddInsert` | при сборке («duplicate step id … after composition») |
| неизвестный якорь; якорь есть, но не в маршрутах области вставки; шаг, который не попал ни в один маршрут; неизвестный токен расы; вставка шире якоря с фильтром | только инструменты, по шаблонам: `insert-anchor-unknown`, `insert-unapplied`, `shared-step-unused`, `unknown-race-token`, `insert-scope-wider-than-anchor` ([tools/README.md](../tools/README.md)) |

Ядро не знает токенов рас (проверяет только, что это строки), а шаг, выпавший из всех маршрутов,
не виден ни в одном собранном маршруте — поэтому такие ошибки ищет валидатор, обходя **шаблоны**
(общие сегменты и вставки), а не собранные маршруты.

Рабочий пример — фикстура `tests/fixtures/core/AdventureAtlas_TestGuides`: область по классу и по
расе, вставка на шаг другой вставки, вставка на якорь с фильтром.

### Таблица наград по классам

Награду квеста, который сдаётся на общем шаге, классы выбирают разную, а общий шаг не несёт
`reward`. Выбор по классу — отдельный вид данных (ядро 0.4.0+), по одному вызову в файле класса:

```lua
AdventureAtlas.AddLibraryData({ rewards = { DRUID = { [92461] = 1, [92463] = 3 } } })
```

* `Engine:GetRewardChoice(questID)`: сначала `reward` шага маршрута (шаг, который сдаёт квест, иначе
  первый шаг, назвавший квест), иначе `rewards[<класс игрока>][questID]`. Индекс — целое ≥ 1, как
  в `reward`; неверное значение игнорируется движком, а при регистрации (`AddLibraryData` /
  `AddRouteData`) форма таблицы проверяется (`Schema.CheckData`): неизвестный токен класса, не
  таблица, ключ — не id квеста, индекс — не целое ≥ 1 — ошибка регистрации (в игре —
  `Registry.errors`, в инструментах — ERROR файла).
* Данные сливаются по виду и по ключу: у каждого класса свой ключ, файлы классов не мешают
  друг другу. Второй вызов с тем же ключом класса **заменяет** таблицу первого. Данные, пришедшие
  после сборки маршрута (модуль загружен позже), только дополняют: уже действующая таблица класса
  остаётся.
* Квесты из таблицы — квесты `turnin` шагов маршрута; отдельно объявлять их для `Data.lua` не нужно.
* `reward` на шаге остаётся для шагов с областью класса (шаг вставки класса).
* Симулятор (`make simulate`) определяет ожидаемый выбор так же, даёт квесту мока столько
  вариантов награды и проверяет индекс, который выбрала автоматика.

### Модуль с общим содержимым и маршрутами

Ядро не знает понятия «модуль»: один аддон может регистрировать общие сегменты, общие вставки,
данные и любое число маршрутов. Так устроен модуль гайдов:

```
addons/AdventureAtlas_Guides/
  AdventureAtlas_Guides.toc  -- ## Dependencies: AdventureAtlas; БЕЗ ## X-AdventureAtlas-Module: library
  Data.lua                   -- (генерируется) один вызов AdventureAtlas.AddLibraryData({...})
  Segments/<Зона>/NN_*.lua   -- AddLibrarySegment: стартовые зоны рас и общий путь
  Classes/<Class>.lua        -- AddLibraryInsert с областью класса + таблица наград класса
  Races/<Race>.lua           -- AddLibraryInsert с областью расы
  Route.lua                  -- RegisterRoute + UseSegments для каждого маршрута (последний файл TOC)
```

* **Порядок TOC — контракт**: сегменты, затем классы, затем расы, затем `Route.lua`. Общие
  вставки у одного якоря применяются в порядке регистрации, поэтому игрок видит там: шаги из
  файла сегмента, затем шаги класса, затем шаги расы. `UseSegments` в `Route.lua` должен найти
  сегменты уже зарегистрированными (иначе — «unknown shared segment … is its file listed in the
  TOC before Route.lua?»).
* Маршруты такого модуля **ничем не владеют**: нет `AddSegment`, `AddInsert`, `AddRouteData`.
  Объявление `## X-AdventureAtlas-Module: library` не ставится (объявленная библиотека не может
  регистрировать маршруты).
* **Строка-страж.** Каждый файл, кроме `Data.lua`, начинается с
  `if not AdventureAtlas.AddLibraryInsert then return end` — см. «Версия ядра».
* Все файлы модуля делят приватную таблицу `local _, ns = ...` (в клиенте и в инструментах): через
  неё файлы сегментов могут передать `Route.lua`, какие стартовые зоны готовы.
* Инструменты: модуль проверяется как набор маршрутов, а его шаблоны — один раз (запись
  `(shared <Модуль>)` валидатора); `Data.lua` — один `AddLibraryData` со всем, на что ссылаются
  общие сегменты и общие вставки, без блоков `AddRouteData` для маршрутов, которые ничем не
  владеют.

Соглашения модуля гайдов (`docs/dev/PLAN.md`, раздел C; проверяет `tests/spec/guides_layout_spec.lua`):

* **Один файл на класс** (`Classes/Warrior.lua` … `Classes/Paladin.lua`): до 12-го уровня в нём по группе вставок
  на стартовую зону (свои якоря, тренеры и квесты; область `race = …` зоны), с 12-го — вставки без расы. Каждая
  вставка несёт `class = "<КЛАСС>"`, каждый шаг — id с префиксом класса (`war-`, `hun-`, `rog-`, `sha-`, `wlk-`,
  `mag-`, `pri-`, `dru-`, `pal-`). Таблица наград — только с известными индексами (БД наград не знает).
* **Один файл на расу** (`Races/<Раса>.lua`, префиксы `orc-`, `tro-`, `tau-`, `und-`, `sky-`): расовые задания и
  верховая езда на 40-м (без чернокнижника и паладина нежити). Файл расы и файл сегмента не ставят вставку на шаг
  классового файла; верховая езда друида попадает между его шагами 40-го уровня порядком файлов (якорь
  `h-40-org-arrive`).
* **Якоря** — шаги пути с явным id (`docs/routes/shared-path.md` §10, `docs/routes/race-*.md` §3). Шаг с фильтром
  расы — якорь только для вставки той же расы. Вставка не берёт и не сдаёт квесты общего пути и не меняет его гейты.
* Обучение у тренера стоит после квестового шага у того же NPC (`WARN lookahead-skip`); крюк дольше ~3 минут без
  ключевой способности — `optional`; непроверенное в игре помечается комментарием `-- CONFIRM` (список —
  `docs/routes/confirm-in-game.md`, `tools/gen_confirm_list.py`).

### Версия ядра

Формат маршрутов остаётся `api = 1`: все расширения аддитивные. Уровень возможностей ядра виден
в `AdventureAtlas.API_MINOR` (у ядра 0.1.x поля не было); `/aa status` показывает версию ядра и
`route API 1.<API_MINOR>`.

| `API_MINOR` | Ядро | Что появилось для модулей маршрутов |
|---|---|---|
| нет | 0.1.x | `RegisterRoute`, `AddSegment`, `AddRouteData` |
| 1 | 0.2.0 | `AddLibrarySegment`, `AddLibraryData`, `UseSegments`, `AddInsert` |
| 1 | 0.3.0, 0.3.1 | синхронизация по уровню, серые и недоступные квесты, задержка автоматики, `questMeta` (API маршрутов не менялся) |
| 2 | 0.4.0 | `AddLibraryInsert`; общие шаги не попадают в маршруты, которым не подходят их фильтры; `aliases` маршрута; таблица наград по классам (`rewards`); ключ `ok` шага и сегмента |
| 2 | 0.5.0 | переименование FastesBoooy → Adventure Atlas: глобальная таблица `AdventureAtlas` (была `FastesBoooy`), папки `AdventureAtlas` / `AdventureAtlas_Guides`, `## Dependencies: AdventureAtlas` (API маршрутов не менялся) |

Ядра до 0.5.0 назывались FastesBoooy и давали глобальную таблицу `FastesBoooy`. Модуль с
`## Dependencies: AdventureAtlas` со старым ядром не загружается вовсе, поэтому проверки ниже нужны для будущих
версий ядра Adventure Atlas.

Со старым ядром модуль, вызвавший функцию, которой в нём нет, получил бы ошибку Lua
(`attempt to call field 'UseSegments' (a nil value)`). Два способа этого избежать:

**Строка-страж в каждом файле** (так делает `AdventureAtlas_Guides`): первая строка каждого файла
модуля, кроме `Data.lua` (в нём только `AddLibraryData`, который есть с 0.2.0):

```lua
if not AdventureAtlas.AddLibraryInsert then return end
```

Со старым ядром модуль тогда не регистрирует ничего, ошибок Lua нет, а ядро показывает свою
подсказку «маршрутов нет». Строка проверяет саму возможность, а не номер версии.

**Проверка версии с сообщением** — в первом файле TOC:

```lua
-- Data.lua (библиотека) / Route.lua (маршрут): первая строка модуля
if (AdventureAtlas.API_MINOR or 0) < 1 then
    print("AdventureAtlas_MyLib: обновите аддон Adventure Atlas (нужно ядро 0.2.0+) / update the Adventure Atlas core (0.2.0+)")
    return
end
```

(`return` прекращает только этот файл; остальные файлы модуля тогда тоже должны проверять
`AdventureAtlas.UseSegments` / `AdventureAtlas.AddLibrarySegment` перед вызовом или полагаться на то,
что без зарегистрированного маршрута их вызовы ничего не ломают.)

Если включены папки аддона под прежним именем (`FastesBoooy`, `FastesBoooy_Guides`, а с версии 0.3 —
`FastesBoooy_Horde`, `FastesBoooy_UndeadPaladin`, `FastesBoooy_SkyborneDruid`), ядро (0.5.0+) один раз за
сессию пишет в чат, что их нужно удалить: их заменил Adventure Atlas.

### `questMeta` в `Data.lua`

`gen_route_data` пишет в `Data.lua` (маршрута и библиотеки) рядом с именами таблицу
`questMeta` для каждого квеста, на который ссылаются шаги модуля и который знает снимок БД:

```lua
    questMeta = {
        [380] = { level = 4, reqLevel = 2, preAny = { 376 } },
        [1063] = { level = 18, reqLevel = 14, preAll = { 1062 } },
        [2581] = { level = 50, reqLevel = 45, items = { 8391, 8392, 8393 } },
    },
```

* `level` — уровень квеста (`-1` — масштабируется с игроком), `reqLevel` — требуемый уровень;
* `preAll` = `preQuestGroup` БД (нужны все), `preAny` = `preQuestSingle` (нужен любой),
  `items` — предметы целей квеста (`objectives.items` БД) — только непустые списки, id отсортированы.

Движок использует их для серых квестов (уровень квеста, когда у клиента нет данных квеста), для
правила недоступных квестов (`accept` квеста, чьи предпосылки — квесты маршрута, которые
игрок уже не возьмёт, считается выполненным; предпосылки вне маршрута считаются выполненными)
и для `collect`: предметы квеста, которого игрок не брал, не собираются, а предметы квеста из
журнала, который маршрут сдаёт после порога синхронизации, остаются целью «Попутно»,
см. [ARCHITECTURE.md](ARCHITECTURE.md), «Синхронизация по уровню, серые и недоступные квесты».
Без `questMeta` (старый `Data.lua`, рукописные данные) всё работает, только эти правила слабее:
серость — только по данным клиента, предпосылки неизвестны. Рукописный `AddRouteData` может
добавить `questMeta` для квестов, которых нет в снимке БД (тот же формат).

### Данные и инструменты

* `Data.lua` модуля маршрута (`make routedata`) перечисляет только то, на что ссылаются его
  **собственные сегменты и вставки**; имена библиотечных шагов приходят из `Data.lua`
  библиотеки (`AddLibraryData`). У модуля с общим содержимым и маршрутами `AddLibraryData`
  покрывает общие сегменты **и общие вставки**; маршрут, который ничем не владеет, блока
  `AddRouteData` не получает.
* Валидатор, симулятор и `gen_route_data` читают `## Dependencies` / `## RequiredDeps` TOC
  модуля и загружают модули `AdventureAtlas_*` из того же каталога раньше него (в песочнице, как
  клиент), затем собирают маршрут кодом `Core/Compose.lua`. Сообщения валидатора о шагах
  модуля-зависимости помечены `[library <модуль>]` (файл — `<модуль>/Segments/…`) и
  выводятся один раз на маршрут; ошибки загрузки самой библиотеки — один раз за запуск.
  Симулятор проигрывает только модули маршрутов (библиотека загружается как зависимость).
  У модуля, который регистрирует и общее содержимое, и маршруты, шаблоны (общие сегменты и общие
  вставки) проверяются один раз, в записи `(shared <Модуль>)`; файлы можно исключать из загрузки
  (`--skip` / `--keep`) и отвечать только за свои (`--own`) — [tools/README.md](../tools/README.md),
  раздел 5.
* luacheck проверяет модули-библиотеки тем же std, что и модули маршрутов (только API
  `AdventureAtlas.*`).
* **Часть библиотеки из стартового состояния** (сегменты пишутся параллельно): валидатор и
  симулятор с `--harness <каталог библиотеки> --segments h-a,h-b --profile race=…,class=…,faction=…
  --state <состояние.json> [--write-state <конец.json>]` собирают синтетический маршрут
  (`RegisterRoute` для одного профиля + `UseSegments` перечисленных сегментов, ничего больше) и
  проверяют / проигрывают его, начиная с уровня, сданных квестов, журнала, камня и точек полёта
  из файла состояния. `--write-state` пишет состояние в конце (тот же формат — звенья цепочки);
  у полного маршрута тоже: `validate_routes.lua --route <id> --write-state f.json`. Подробно —
  [tools/README.md](../tools/README.md), раздел «Harness».

## Валидация

`make validate` (см. `tools/validate_routes.lua`) проверяет каждый маршрут по
снимку базы Forever (`tools/data/forever_db.lua`): существование квестов,
доступность для расы/класса/фракции, требования по уровню (симуляция опыта),
цепочки (pre-quests, exclusive), принадлежность NPC и расстояние от `at` до
спавна, ёмкость журнала, тренеров/полётчиков/трактирщиков. Предупреждение, которое автор
проверил и оставил, принимается ключом [`ok`](#принятые-предупреждения-ok); строгий режим
(`--strict --end-level`) требует, чтобы непринятых предупреждений не осталось и маршрут
заканчивался на плановом уровне. Отдельные значения снимка БД (опыт квеста, раса, которой он
доступен) исправляются поправками в `tools/overrides` (см. `tools/overrides/README.md`).
Сводный отчёт по всем маршрутам — [VALIDATION.md](VALIDATION.md) (`make report`), команды и коды
сообщений — [tools/README.md](../tools/README.md).
