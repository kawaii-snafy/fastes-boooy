# Архитектура AdventureAtlas

Монорепозиторий: ядро-аддон + аддоны-модули маршрутов + офлайн-инструменты
проверки. Целевой клиент — **World of Warcraft: Forever** (билд 1.60.1.x,
`## Interface: 16001`, современный API `C_QuestLog`/`C_GossipInfo`/`C_Map`).

```
addons/
  AdventureAtlas/                 ядро (без контента)
  AdventureAtlas_Knowledge/       данные базы знаний (LoadOnDemand, ## X-AdventureAtlas-Module: data):
    Quests.lua                    квесты Орды из снимка БД (генерируется: make knowledge)
  AdventureAtlas_Guides/          все гайды: один маршрут на расу и класс (id <раса>-<класс>, 1-60)
    Data.lua                      имена квестов / NPC / мест, questMeta (генерируется: make routedata)
    Segments/<Зона>/              стартовые зоны (Tirisfal, Zephras, Durotar, Mulgore): классово-нейтральные
                                  сегменты, каждая зона объявляет себя в ns.startZones
    Segments/Shared/              общий путь 12-60 (h-12 … h-56): один для всех рас
    Classes/<Класс>.lua           шаги класса: общие вставки (AddLibraryInsert) на якорях пути, таблица
                                  наград класса (AddLibraryData{ rewards = ... })
    Races/<Раса>.lua              шаги расы (столица, верховая езда) — тоже общие вставки
    Route.lua                     регистрирует маршруты рас, чьи стартовые зоны объявили себя
tools/                            валидатор маршрутов, генераторы, симулятор
  data/forever_db.lua             снимок БД Forever (квесты/NPC/объекты/предметы/зоны)
  data/forever_api.lua            список API/событий/шаблонов клиента Forever
  overrides/                      поправки к снимку БД с источником и отметкой «проверено в игре»
tests/                            busted-спеки + мок WoW API
docs/                             документация (маршруты: docs/routes/)
```

Ядро 0.4.0 позволяет одному аддону регистрировать общие сегменты, **общие вставки** классов и
рас (`AddLibraryInsert`) и много маршрутов сразу. На этом построен модуль гайдов
`AdventureAtlas_Guides` (28 маршрутов «раса + класс» 1-60 по плану `docs/dev/PLAN.md`: пять стартовых
зон в `Segments/<Зона>/`, общий путь с 12-го уровня в `Segments/Shared/`, шаги девяти классов в
`Classes/<Класс>.lua`, шаги пяти рас в `Races/<Раса>.lua`, таблица маршрутов в `Route.lua`;
соглашения о якорях и вставках — `docs/routes/shared-path.md` §10, `docs/ROUTE_FORMAT.md`). Он заменил прежние модули `FastesBoooy_Horde` (библиотека 22-60),
`FastesBoooy_UndeadPaladin` и `FastesBoooy_SkyborneDruid`; прежние id маршрутов остались
псевдонимами (`aliases`). Его форму в малом повторяет фикстура
`tests/fixtures/core/AdventureAtlas_TestGuides`. Модуль данных не обязан состоять только из
маршрутов: ядро принимает модуль с одним общим содержимым, с одними маршрутами или с тем и
другим, а `AddLibraryData` сливает данные любого вида по виду и ключу (следующий этап после
гайдов — атлас, `docs/dev/ATLAS.md`).

## Ядро: модули и ответственность

Все файлы ядра получают `local ADDON, ns = ...`. Публичная таблица — глобальная
`AdventureAtlas` (= `ns.public`), внутреннее API — `ns.*`.

| `Core/Schema.lua` | **контракт формата маршрутов** (чистый Lua; общий с инструментами) |
| `Core/Compose.lua` | **сборка маршрута** из своих сегментов, сегментов библиотеки (`UseSegments`), общих вставок (`AddLibraryInsert`) и вставок маршрута (`AddInsert`); хранилище общего содержимого (`AddLibrarySegment` / `AddLibraryInsert` / `AddLibraryData`). Чистый Lua, общий с инструментами (см. ниже) |

## Общие сегменты и вставки (`Core/Compose.lua`)

Общее содержимое — классово-нейтральные сегменты `AdventureAtlas.AddLibrarySegment{...}`, общие
вставки `AdventureAtlas.AddLibraryInsert{...}` и данные `AdventureAtlas.AddLibraryData{...}` — попадает в
одно хранилище `ns.Registry.library` (`Compose.NewLibrary`): сегменты нормализуются
`Schema.AddSegment` один раз (ошибки формата — один раз, при регистрации), id сегментов и шагов
уникальны во всём общем содержимом. Его регистрирует сам модуль маршрутов (`AdventureAtlas_Guides`:
файлы `Segments/`, `Classes/`, `Races/` в TOC раньше `Route.lua`) или отдельный модуль-библиотека,
от которого модуль маршрутов зависит (`## Dependencies: AdventureAtlas, <библиотека>` — клиент грузит
её раньше; так были устроены модули до 0.4, так устроены фикстуры `AdventureAtlas_TestLib` /
`AdventureAtlas_TestComposed`). Маршрут вызывает `UseSegments(routeId, {...})` и, при нужде,
`AddInsert(routeId, {after|before, steps})`.

* Первый такой вызов делает маршрут **составным**: его собственные сегменты переезжают в
  `route.own` (та же форма, что у маршрута: `segments/steps/stepById/segmentById`; туда же
  добавляют последующие `AddSegment`), а `route.segments/steps/stepById/segmentById` строит
  `Compose.Build`: свои сегменты (кроме названных в `UseSegments`) → элементы `UseSegments`
  (копии шагов библиотеки для этого маршрута — у разных маршрутов свои `index`; нормализованные
  `actions` общие, движок шаги не меняет) → вставки по порядку вызовов (после/перед якорем,
  после прежних вставок у того же якоря; шаги вставки получают сегмент якоря и id
  `<якорь>+<n>`, если id не задан). Данные библиотеки подмешиваются в `route.data` под данными
  маршрута. Маршрут без `UseSegments`/`AddInsert` не трогается вовсе.
* **Общие вставки** (`AdventureAtlas.AddLibraryInsert{ after | before, class, race, faction, steps }`,
  ядро 0.4.0) хранятся в том же хранилище (`library.inserts`, порядок регистрации) и применяются
  к каждому маршруту с `UseSegments`, среди собранных шагов которого есть якорь. `Compose.Build`
  идёт одним упорядоченным проходом: сначала общие вставки в порядке регистрации, потом вставки
  маршрута в порядке вызовов; вставка, якоря которой ещё нет, ждёт, а когда шаг с таким id
  поставлен, проход начинается сначала — поэтому порядок у одного якоря всегда равен порядку
  списка, даже если вставка зарегистрирована раньше той, что даёт ей якорь. Каждый маршрут
  получает свои копии шагов (`route.libCopies[шаблон]`: копия существует ⇔ шаг собран в этот
  маршрут; копии стабильны между пересборками), с метками `inserted`, `shared`, `library`,
  `file`, `anchor`, `insertSide`. Якорь должен иметь явный id (`Schema.AddSegment` помечает
  позиционные id `step.autoId`). Правила и таблица ошибок — `docs/ROUTE_FORMAT.md`, «Общие
  вставки».
* **Отсечение по области маршрута.** Общий шаг (шаг общего сегмента или общей вставки), чьи
  фильтры `class`/`race`/`faction` не могут совпасть с маршрутом (`Schema.FiltersCanMatchRoute`:
  не пересекаются с `route.classes` / `races` / `faction`), в маршрут не собирается. У маршрута
  с одной расой и одним классом «может совпасть» значит «будет показан»: файл класса не занимает
  память в маршрутах других классов, шаг-альтернатива с фильтром по расе служит якорем только
  своим расам. Сегмент, из которого не осталось ни одного шага, в маршрут не попадает. Маршрут
  без `classes` / `races` получает всё, фильтрует движок.
* Сборка **ленивая**: вызовы только записывают, что сделать, и помечают маршрут `dirty`;
  `Registry:Finalize` собирает его при первом чтении — `Registry:Get/List`, `Matching/Select`
  (только маршруты, подходящие персонажу по фракции/расе/классу), `Engine:BuildSteps` (после
  `ROUTES_CHANGED`) и `Engine:Start` (`PLAYER_LOGIN`: выбор маршрута, до вывода числа ошибок
  регистрации). Маршрут другого класса/расы собирается, только когда его выбирают
  (`/aa route <id>`): паладин не тратит ~1-2 МБ на маршрут друида, а при 28 маршрутах в одном
  модуле собирается один. Панель настроек и `/aa routes` показывают только подходящие персонажу
  маршруты (`Registry:Matching`), остальные — числом; `/aa routes all` печатает id и названия всех
  маршрутов из `Registry:List(true)` — без сборки (`Registry:IsComposed(route)` говорит, собран ли
  маршрут; строка «Шагов: N» в подсказке — только для собранного). Поэтому
  вставки можно регистрировать до или после `UseSegments`, а якорем может быть шаг библиотеки.
  Изменение общего содержимого помечает все составные маршруты.
* **Прежние id маршрутов** (`RegisterRoute{ aliases = ... }`): `Registry.aliases[старый id] =
  маршрут`; `Registry:Get` ищет сначала по id, потом по алиасу. `Engine:ActivateRoute` переписывает
  `cdb.route`, `cdb.cursorHintRoute`, `cdb.syncFloor.route` и `cdb.syncDismissed.route` с алиаса
  на id маршрута; другой миграции сохранённых данных нет. Отметки шагов хранятся по id шага.
* **Данные общего содержимого** (`AddLibraryData`) подмешиваются в `route.data` при сборке, по
  виду и по ключу (`Compose.MergeData`; значения самого маршрута важнее). Виды: имена (`quests`,
  `npcs`, `objects`, `items`, `places`), `questMeta` и **таблица наград по классам**
  `rewards[<CLASS>][questID] = индекс` — первый вид данных, кроме имён и `questMeta`, который
  читает движок. Второй вызов с тем же ключом класса заменяет первый; данные, пришедшие после
  сборки маршрута, только дополняют.
* Ошибки сборки (неизвестный сегмент библиотеки, неизвестный якорь, id шагов/сегментов,
  совпавшие только после сборки) записываются в `Registry.errors` **один раз** на маршрут
  (повторная сборка не дублирует сообщение). `UseSegments`/`AddInsert` до `RegisterRoute` —
  ошибка + очередь, как у `AddSegment`.
* `Engine:Evaluate` идёт по всему маршруту (1 700+ шагов) на каждом обновлении, поэтому не
  создаёт таблиц на каждый вызов: контекст, кэш состояний квестов (запись обновляется на месте,
  помечена номером оценки `ctx.gen` — `Steps.QuestState`), счётчики предметов и массив `done`
  (два буфера: `Engine.done` — всегда последняя завершённая оценка) переиспользуются.
* Движок получает обычный плоский список шагов: фильтры, `bg` (сегмент якоря для вставок),
  `optional`, граница перемотки, брошенные квесты и `cursorHint` по id работают без изменений.
* Офлайн-инструменты загружают `Core/Schema.lua` и `Core/Compose.lua` в один `ns`
  (`tools/lib/route_loader.lua: Loader.LoadSchema`), модули-зависимости `AdventureAtlas_*` из
  `## Dependencies`/`## RequiredDeps` — раньше модуля, в песочнице, каждый со своей таблицей
  `ns` — и собирают маршрут тем же `Compose.Build`. Итог в игре, в валидаторе, симуляторе и
  `gen_route_data` одинаков.

## Движок

1. При входе: выбирается маршрут (сохранённый для персонажа или `default`,
   подходящий по фракции/расе/классу).
2. Шаги фильтруются по `class/race/faction` → плоский список.
3. **Курсор** = первый шаг, который не выполнен и не `bg`. `bg`-шаги, через
   которые прошёл курсор, попадают в список «попутно», пока не будут выполнены
   или пока их квест не сдан/брошен (квест из `accept` ещё не взят — шаг
   остаётся). Перемотка на `bg`-шаги не действует, пока игрок в том же
   сегменте; когда курсор/перемотка ушли в более поздний сегмент, `bg`-шаги
   прошлых сегментов перематываются как обычные (их transient/`collect`
   считаются выполненными), чтобы холодный старт не возвращал давно пройденные
   цели. Выполненный `bg`-шаг с `collect`/transient-действиями запоминается
   (`AdventureAtlasCharDB.bgDone`, только оптимизация).
4. Выполненность шага = AND по действиям (см. `docs/ROUTE_FORMAT.md`).
   Transient-действия отмечаются событиями, пока шаг текущий или в списке
   «попутно» (окно тренера/торговца — при закрытии, для шагов, наблюдаемых
   в момент открытия, у которых `npc` содержит NPC окна (`UnitGUID("npc")`) или
   `npc` не задан; карта полётов — при открытии; смена точки привязки;
   прибытие). Клиент шлёт и старое событие (`TRAINER_CLOSED` и т. п.), и
   `PLAYER_INTERACTION_MANAGER_FRAME_*` — одно окно засчитывается один раз.
   **Перемотка** (`Engine:Evaluate`): граница = max(опорный шаг, сохранённая
   отметка самого дальнего шага `cursorHint`). Опорный шаг — последний не-`bg`
   шаг с действием `accept`/`turnin`/`complete`, все stateful-действия которого
   выполнены (или он отмечен вручную); `level` опорой **не** является (уровень,
   набранный раньше за счёт rested-опыта, не должен молча пропускать более ранние
   `sethearth`/`train`/`fp`), как и `abandon` (выполнен «пусто») и `collect`
   (предметы могут быть в сумках случайно). Шаги до границы: transient-действия и
   `optional` считаются выполненными; из stateful — только `collect` (предметы
   потрачены более поздней сдачей) и `accept` квеста, который бросает более
   поздний шаг маршрута (`abandonAfter[i]` → `ctx.abandonedLater`, иначе после
   `abandon` курсор вернулся бы к `accept`). Прочие stateful-действия всегда
   читаются из игры, поэтому холодный старт с пустыми SavedVariables приходит
   на верный шаг; неизвестны только transient-шаги после последнего опорного.
   **Брошенные игроком квесты** (`Engine.givenUp[q] = j` → `ctx.givenUp`,
   сравнивается с `ctx.index`). Квест «оставлен», если (а) более поздний не-`bg`
   шаг с его `complete`/`turnin` отмечен (кнопка «Вперёд» — `Engine:Skip`, `/aa skip`,
   `/aa next`) или `optional` и лежит до границы перемотки (`j` = этот шаг), или (б) игрок
   бросил его вручную — в любом порядке с пропуском (`AdventureAtlasCharDB.gaveUp`, `j` = следующий
   `accept` того же квеста или конец маршрута). Для (б) на `QUEST_REMOVED` (кроме
   `wasReplayQuest`) движок запоминает натуральный курсор и через 0,5 с
   (`Engine:GiveUpQuest`) проверяет, что квест не сдан (`Compat.IsQuestTurnedIn`:
   при сдаче приходят и `QUEST_TURNED_IN`, и `QUEST_REMOVED`) и не в журнале; пока
   проверка ждёт, квест удерживается до запомненного шага — курсор не мигает назад
   и автоматика не берёт квест. Если `accept` квеста лежит до курсора (запомненный
   натуральный курсор или `cursorHint`; иначе квест был взят заранее — ничего не
   делается) и в этом экземпляре квеста (до следующего `accept`) нет явного
   `abandon` (маршрут ведёт квест сам), невыполненные не-`bg` шаги, все действия
   которых — `complete`/`turnin` этого квеста, получают отметку `skipped` (их id —
   в `gaveUp[q].steps`, шаг `accept` — в `gaveUp[q].accept`), в чат — одна строка.
   Если всё уже покрыто отметками игрока / пройденными `optional`-шагами, запись не
   создаётся. Пока квест не в журнале и не сдан, его `accept` и (на не-`bg` шагах)
   `complete`/`turnin` до индекса `j` считаются выполненными: курсор не прыгает
   назад, автоматика не берёт квест снова, смешанный шаг (`turnin = { Q, R }`) ждёт
   только остальных действий, `bg`-шаг с его `accept` уходит из списка «попутно».
   Отметки гайда не служат опорным шагом перемотки (иначе отметка далёкой сдачи
   перемотала бы `go`/`train` перед ней). Запись и её отметки снимаются, когда квест
   снова взят вручную (`QUEST_ACCEPTED` или квест найден в журнале при пересчёте;
   кроме случая, когда его взяли для следующего `accept` того же квеста в окне
   автоматики — это уже новый экземпляр) или сдан, по «Назад» сразу после
   оставления или на одном из её отмеченных шагов, по `/aa reset`. Холодный старт
   с пустыми SavedVariables о брошенном квесте не знает: курсор встанет на его
   `accept` (как и после потери отметок «Пропустить»).
5. Пересчёт — по событиям квестов/опыта/сумок/зоны с троттлингом и по тикеру
   позиции (для `go/fly/hearth`), а также при смене настроек `levelSync` /
   `levelSyncMargin` / `skipGray` (`SETTINGS_CHANGED`).
6. Прогресс сохраняется по персонажу: id маршрута, ручные отметки, пропуски,
   брошенные вручную квесты (`gaveUp`), порог синхронизации по уровню (`syncFloor`) и
   отказ от предложения (`syncDismissed`).
7. Навигация: «Назад» (`Engine:Prev`) — закрепить предыдущий шаг и снять с него
   отметку «пропущен / выполнен вручную», если она есть (и когда вид уже закреплён: пропущенный шаг
   не всегда стоит прямо перед курсором); единая кнопка «вперёд» интерфейса — `Engine:Forward()`: если вид
   закреплён «Назад», сдвигает закрепление вперёд (ничего не отмечая), иначе пропускает
   текущий шаг (`Skip`). `Engine:GetUpcoming(n)` отдаёт только **невыполненные** шаги после
   текущего (выполненные в игре, отмеченные, «пустые» и шаги ниже порога синхронизации —
   не показываются).

### Синхронизация по уровню, серые и недоступные квесты

Игрок, обогнавший маршрут (подземелья, группа, другой гайд), не должен возвращаться в
зону низкого уровня. Три механизма, все в `Engine:Evaluate` (одним проходом
`Engine:ComputeVoid` вперёд по шагам, с мемоизацией на оценку):

* **«Пустые» действия квестов** (`Engine.void[action] = причина` → `ctx.void`, см.
  `Core/Steps.lua`): действие считается выполненным, хотя квеста нет ни в журнале, ни среди
  сданных — игрок его не брал.
  * `gray` (настройка `skipGray`, по умолчанию вкл.): `accept` квеста, серого для уровня игрока,
    **в сегменте, который игрок перерос** (`уровень > levels[2]` сегмента шага; сегмент без
    `levels` — всегда). Серость — как у клиента: `Compat.IsQuestGray` спрашивает
    `C_QuestLog.IsQuestTrivial(questID)`, если у клиента есть данные квеста (`HaveQuestData`;
    у незагруженного квеста API может ошибаться — так же делает Questie на Forever), иначе
    правило FrameXML `GetRelativeDifficultyColor`: серый, если `уровень − уровень квеста >
    зелёный диапазон`; уровень квеста — из `questMeta` данных маршрута, диапазон —
    `C_QuestLog.GetTrivialRange()` (Forever), иначе `UnitQuestTrivialLevelRange("player")`, иначе
    классическое правило (`Compat.FallbackTrivialRange`: серый уровень 0 до 5-го, `L − ⌊L/10⌋ − 5`
    до 39-го, `L − ⌊L/5⌋ − 1` до 59-го, 48 на 60-м; то же, что `DB.GreyLevel` валидатора). Уровень
    квеста ≤ 0 (масштабируется) — не серый. Кэш по уровню, сбрасывается при `QUEST_DATA_LOADED`.
    Квест **не пропускается**, если он — предпосылка (`questMeta` `preAll`/`preAny`) более позднего
    квеста маршрута, который не сдан, не в журнале, к которому маршрут ещё ведёт (хотя бы один его
    `accept` не пройден без игры: не отмечен, не ниже порога синхронизации, не `optional` не-`bg` шаг до
    границы перемотки, квест не оставлен) и который сам не пропускается как серый либо защищён
    (транзитивно: цепочки, открывающие хорошие квесты, сохраняются; для `preAny` — если другая
    альтернатива уже сдана, квест не нужен). Квест, который игрок прошёл мимо или от которого
    отказался, цепочку не держит: так пройденный маршрут остаётся пройденным и при холодном
    старте (цепочка 1424 > 1429 > 1444 ведёт к необязательному подземелью 1445; персонаж, который
    перепрыгнул её синхронизацией и закончил маршрут, без этого правила после потери
    SavedVariables стоял бы на `accept` 1424). Ограничение «перерос сегмент» оставляет квесты,
    которые автор маршрута берёт серыми нарочно (например, 81952 «Everyday Etiquette», 45-й, в
    h-56 на 57-58-м): обычный прогон маршрута ведёт себя как прежде.
  * `unreachable`: `accept`, чьи предпосылки-квесты маршрута уже не выполнить: в `preAll` есть
    «мёртвый» квест маршрута, или `preAny` непуст и **все** его члены — мёртвые квесты маршрута.
    Предпосылки, которых маршрут не берёт, считаются выполненными. Квест маршрута `p` мёртв, если
    он не сдан, не в журнале, а все (минимум один) `accept` квеста `p` до этого шага «не взяты».
  * `orphan`: `complete`/`turnin` квеста, которого нет ни в журнале, ни среди сданных, если все
    (минимум один) его `accept` до этого шага или в том же шаге «не взяты». Поэтому пропуск
    («Вперёд») шага `accept` больше не оставляет его сдачу блокировать курсор. Так же `orphan` —
    `collect` (после прохода, когда известны все `accept`): его квесты — квесты маршрута, у которых
    предмет — цель (`questMeta` `items`), иначе квесты `complete`/`turnin` того же шага; «пустой»,
    если ни один из них не возможен (мёртв) и не нужен (сдан), и хотя бы один мёртв — гайд не шлёт
    собирать предметы для квестов, которых у игрока нет.
  * `floor`: прочие действия шага ниже порога синхронизации, который остаётся целью «Попутно»
    (см. ниже) — выполненными считаются все действия, кроме оставленных.
  * `accept` «не взят», если квест не в журнале и не сдан, а действие выполнено без игры: шаг
    отмечен («Вперёд» / `/aa next` / `/aa skip`), лежит ниже порога синхронизации, это `optional` не-`bg` шаг до границы
    перемотки, квест оставлен (`givenUp`, кроме ждущей проверки `QUEST_REMOVED`) или сам `accept` —
    `gray`/`unreachable`. Как только квест появляется в журнале (взят вручную), его шаги снова
    нужны.
  * «Пустые» действия не служат опорой перемотки (опорный шаг считается до прохода) и не
    принимаются автоматикой (`GetAcceptQuests`).
* **Синхронизация по уровню** (настройки `levelSync` = `"ask"` | `"auto"` | `"off"`, по умолчанию
  `"ask"`; `levelSyncMargin` = 0…5, по умолчанию 2). Сегмент с `levels` **перерос по уровню**, если
  `уровень ≥ levels[2] + запас`. Если перерос сегмент натурального курсора, предлагается первый
  более поздний сегмент, который не перерос и в котором есть невыполненный не-`bg` шаг:
  `Engine:GetSyncSuggestion()` → `{ level, from, fromIndex, to, toIndex, toStepId, margin }`
  (`from`/`to` — таблицы сегментов маршрута: `id`, `title`, `levels`). Внутреннее сообщение
  `SYNC_SUGGESTION(suggestion | nil)` — при каждом появлении/изменении/исчезновении (вход,
  повышение уровня, смена маршрута, движение курсора, смена настроек); таблица предложения не
  меняется, пока не изменились `from`/`to`/`toIndex`/уровень. В режиме `"off"` предложений нет,
  в `"auto"` движок применяет синхронизацию сам (строка в чат), предложение не показывается.
  * Предлагается только переход, который что-то **экономит** (`Engine:SyncSkipsContent`): между
    натуральным курсором и `toIndex` есть невыполненный не-`bg` шаг с `accept` квеста, которого нет
    в журнале, который не сдан, не «пустой» и который маршрут сдаёт до `toIndex` (новый материал
    перерощенного отрезка). Квесты журнала (их доделывают по пути), «мосты» (сдаются после
    `toIndex`), тренер / перемещения / сервисы и уровневые шаги причиной не служат: игрок, идущий
    по маршруту с опережением на пару уровней, не получает предложение на каждом последнем шаге
    сегмента, а режим `"auto"` не выбрасывает сдачи и тренировку. Правило действует и для
    явного `ApplySync`/`/aa sync`.
  * `Engine:ApplySync()` (кнопка баннера, `/aa sync`; работает и в режиме `"off"`) — порог
    `AdventureAtlasCharDB.syncFloor = { route, stepId, from, to, level, at, hint, keep, prev }`: шаги
    до `stepId` (и `bg`-шаги) считаются выполненными, **кроме целей «Попутно»** ниже; строка в чат;
    обычные `STEP_CHANGED` / `PROGRESS_UPDATED`, затем `SYNC_APPLIED(record)`. `Engine:GetLastSync()`
    — `{ at = GetTime(), record }` последней синхронизации сессии, пока её порог действует (ссылка
    «Вернуть»).
  * **Цели ниже порога** (`Engine.floorKeep[i]`, каждая оценка; в списке `GetBackground()`, свои
    действия считаются без перемотки, прочие действия шага — `void` `floor`):
    * квест в журнале, который маршрут сдаёт на пороге или позже, не выполнен — его `complete` и
      `collect` его предметов (`questMeta` `items`, или `collect` в шаге с таким `complete`)
      ниже порога (иначе сдача после порога стояла бы без подсказки, как выполнить квест);
    * квест в журнале, готовый к сдаче, — его `turnin` ниже порога;
    * пропущенные сервисные визиты (`record.keep = { { id, type }, ... }`, `Engine:SkippedServices`
      при `ApplySync` из невыполненных не-`bg` не-`optional` шагов между курсором и порогом плюс
      ещё не сделанные визиты прошлого порога): последний `train`; последний `sethearth`, если
      дальше есть `hearth` в это место до следующего `sethearth`; по месту последний `fp`, если
      дальше есть `fly` туда до следующего `fp` этого места. Визит держится, пока натуральный
      курсор не прошёл шаг, которому он нужен (`Engine:KeepUntil`: до следующего не-`optional`
      `train` — иначе до конца маршрута; до последнего такого `hearth` / `fly`); сделанный (флаг
      окна / привязки — только в памяти) или ненужный визит удаляется из `record.keep`
      (сохраняется в SavedVariables).
    * Квесты журнала, которые маршрут сдаёт только ниже порога и которые не выполнены, — брошены
      порогом: `Engine:GetDroppedQuests()`; `ApplySync` перечисляет их в чате (выполнить самому или
      отменить).
    * Подсказки (`Core/Steps.lua` `Describe`, строки `note` с `hint = true`): шаг `fly` к месту,
      чей пропущенный `fp` ещё ждёт (`Engine:FlightPathPending`), и шаг `hearth`, когда при
      действующем пороге камень привязан не к месту шага (`Engine:HearthBindMismatch`,
      `Compat.BindLocation` + `Engine:PlaceMatches`). Окно шагов в «Попутно» не показывает строки
      `void == "floor"`.
  * Порог проверяется по маршруту: чужой маршрут или шаг, которого нет в отфильтрованном
    списке, — порог не действует. «Назад» за порог только закрепляет вид (отметки не снимаются).
  * `Engine:DismissSync()` — не предлагать для этого сегмента `from` до следующего повышения
    уровня (`syncDismissed = { route, segment, level }`, сохраняется).
  * `Engine:UndoSync()` — только для порога активного маршрута (порог другого маршрута остаётся
    ему) — вернуть предыдущий порог (один уровень `prev`) или убрать порог и
    вернуть отметку самого дальнего шага (`cursorHint`) момента синхронизации (иначе пройденные
    шаги-перемещения остались бы перемотанными); сегмент `from` не предлагается до следующего
    повышения уровня (иначе режим `"auto"` сразу прыгнул бы снова); `SYNC_UNDONE`.
  * `/aa reset` (`Engine:Reset`) забывает порог и отказ.
  * Холодный старт без SavedVariables теряет порог: предложение (или автоприменение) появляется
    снова.
  * Поэтому **`levels` сегментов должны быть точными** (`docs/ROUTE_FORMAT.md`).
* Стоимость: проход `ComputeVoid` ≈ 1–2 мс на маршруте из 1 713 шагов (мок, Lua 5.1); одна оценка
  (`Evaluate`) ≈ 5–6 мс против ≈ 3,6–5 мс до него (спек `core_sync_spec.lua` «performance» требует
  `Refresh` < 60 мс).

## Автоматизация (только квесты маршрута)

* Принимаются квесты из `accept` в окне «текущий шаг + N следующих» (+ фоновые), кроме
  «пустых» (серые и недоступные квесты, которые маршрут пропускает; вручную их взять можно).
* Сдаются квесты из `turnin` в любом месте маршрута, если квест выполнен.
* Награда выбирается автоматически, если вариантов ≤ 1 или выбор задан: `reward` шага, иначе
  таблица наград класса из данных маршрута (`Engine:GetRewardChoice`);
  иначе автоматика останавливается и пишет в чат «Выберите награду за … сами» (окно
  награды остаётся открытым; внутреннее сообщение `REWARD_CHOICE_NEEDED(questID, n)` —
  для модулей, которые захотят его подсветить; ядро само ничего не подсвечивает).
* Удерживаемый **Shift** отключает автоматику на текущий диалог: Shift,
  нажатый при открытии окна (GOSSIP_SHOW / QUEST_GREETING / QUEST_DETAIL /
  QUEST_PROGRESS / QUEST_COMPLETE), действует до закрытия диалога с этим NPC
  (`GOSSIP_CLOSED` без продолжения, `QUEST_FINISHED`), даже если его отпустить.
* **Задержка.** Действия не выполняются в обработчике события: каждое (AcceptQuest через
  `Compat.AcceptDialogQuest`, CompleteQuest, GetQuestReward, выбор квеста в госсипе /
  приветствии, реплика госсипа) планируется через `C_Timer.After(autoDelay + random()·autoDelayJitter)`
  (настройки, по умолчанию 0,5 с + 0…0,3 с; пределы 0…3 и 0…1 — `ns.SETTING_RANGES`, при загрузке
  сохранённые значения подрезаются; панель настроек и `/aa delay`). Популярные аддоны действуют
  мгновенно (Questie, RestedXP — прямо в обработчике, Guidelime — `C_Timer.After(0.01)`); видимая
  пауза выглядит как игрок, читающий окно.
  * Каждый обработчик сначала *планирует* действие (`Automation:Plan…` → `{ key, run }`, например
    `accept 363`, `reward 380 2`, `greeting accept 364 2`, `gossip option <шаг> <№> <id>`), подсказки
    в чат (награда, журнал полон, PvP, деньги) пишутся сразу. Таймер планирует **заново** и
    выполняет действие, только если получилось то же самое: тот же токен диалога, то же окно
    (`Compat.GetDialogQuestID` / списки госсипа и приветствия / реплика шага), автоматика не
    приостановлена (Shift, настройки), нет боевой блокировки, квест всё ещё подходит (окно
    маршрута, выполнимость, правило награды). Иначе действие молча отбрасывается.
  * Токен диалога (`Automation.serial`) растёт на каждом событии открытия/закрытия окна:
    QUEST_DETAIL / QUEST_PROGRESS / QUEST_COMPLETE / QUEST_GREETING / GOSSIP_SHOW /
    GOSSIP_CLOSED / QUEST_FINISHED. Ждёт не больше одного действия: новое событие окна заменяет
    его, повторное событие того же окна (клиент может прислать его дважды) планирует то же
    действие заново — итог одно действие; повторный план с тем же токеном и ключом ничего не
    добавляет. Исключение: `GOSSIP_CLOSED(true)` (госсип уступает место окну квеста) не сбрасывает
    действие окна квеста — клиент может прислать его после события окна квеста.
  * Shift (`MODIFIER_STATE_CHANGED`), нажатый во время паузы, отменяет ждущее действие и
    приостанавливает автоматику до конца диалога (как Shift при открытии окна).
  * `autoDelay = 0` — прежнее поведение: действие выполняется сразу в обработчике события
    (добавка при этом не используется).
  * Тесты и симулятор ждут автоматику по часам мока (`m:Advance`): `H.waitAuto` в спеках,
    в `tools/simulate_routes.lua` — с настройками по умолчанию; симулятор проверяет, что в самом
    событии окна ничего не вызвано, и считает «delayed actions».

## Проверка (без запуска игры)

| Команда | Что проверяет |
|---|---|
| `make lint` | luacheck со стандартом `forever`, сгенерированным из списков API клиента Forever: любой вызов несуществующей функции/поля API — ошибка; модули маршрутов видят только `AdventureAtlas.*` и базовый Lua |
| `make test` | busted: схема, сборка, движок, автоматика, навигация, UI на моке WoW API (мок разрешает только методы виджетов, существующие в Forever); инструменты (валидатор, отчёт, симулятор, сборка) |
| `make validate` | валидатор маршрутов по снимку БД Forever с поправками `tools/overrides` (составные маршруты — вместе с библиотеками-зависимостями). У модуля с общим содержимым и маршрутами шаблоны (общие сегменты и вставки) проверяются один раз. Принятые предупреждения (`ok`), строгий режим и числовые критерии (уровень в конце, бюджеты гринда) — `VALIDATE_FLAGS` |
| `make simulate` | «прогон» каждого маршрута через настоящий движок на моке: каждый шаг должен завершаться ровно тем действием, которое он требует, награда — выбором маршрута. По процессу на маршрут, `JOBS` процессов одновременно (список маршрутов — `simulate_routes.lua --list-routes`; модуль с ошибкой загрузки роняет цель) |
| `make simulate-sync` | «игрок обогнал маршрут»: маршруты `SYNC_ROUTES` со свежим персонажем уровней 10 / 23 / 35 / 48 (`--ahead L`), прыжок посреди сегмента с журналом (`--ahead-at`), игра с опережением (`--level-plus`); предложения синхронизации применяются, `accept` с невыполнимыми предпосылками-квестами маршрута — ошибка («unreachable accept»). Все маршруты — `make simulate-sync-full` (ночной запуск CI) |
| `make check` | всё перечисленное и фикстуры: то, что запускает CI (`.github/workflows/ci.yml`); `make check-fast` — быстрый круг (lint, валидатор, фикстуры, симуляция одного маршрута) |
| `make report` | `docs/VALIDATION.md`: сводный отчёт валидатора — сводка по маршрутам, сравнение путей, сообщения об общих шагах один раз для всех маршрутов, пороги уровня, собственные сообщения каждого маршрута |

Команды, опции и коды сообщений — [tools/README.md](../tools/README.md).
