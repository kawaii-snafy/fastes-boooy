# Архитектура FastesBoooy

Монорепозиторий: ядро-аддон + аддоны-модули маршрутов + офлайн-инструменты
проверки. Целевой клиент — **World of Warcraft: Forever** (билд 1.60.1.x,
`## Interface: 16001`, современный API `C_QuestLog`/`C_GossipInfo`/`C_Map`).

```
addons/
  FastesBoooy/                    ядро (без контента)
  FastesBoooy_UndeadPaladin/      маршрут: Нежить-паладин (Орда) 1-22
  FastesBoooy_SkyborneDruid/      маршрут: Скайборн-друид (Орда, Windshaper) 1-22
  FastesBoooy_Horde/              (план) библиотека общих сегментов Орды 22-60: маршруты классов
                                  берут их через UseSegments и добавляют классовые вставки
tools/                            валидатор маршрутов, генераторы, симулятор
  data/forever_db.lua             снимок БД Forever (квесты/NPC/объекты/предметы/зоны)
  data/forever_api.lua            список API/событий/шаблонов клиента Forever
tests/                            busted-спеки + мок WoW API
docs/                             документация
```

## Ядро: модули и ответственность

Все файлы ядра получают `local ADDON, ns = ...`. Публичная таблица — глобальная
`FastesBoooy` (= `ns.public`), внутреннее API — `ns.*`.

| Файл | Ответственность |
|---|---|
| `Core/Init.lua` | неймспейс, версия, диспетчер событий (`ns:On(event, fn)`), колбэки (`ns:Fire(msg, ...)` / `ns:Listen(msg, fn)`), SavedVariables (`FastesBoooyDB`, `FastesBoooyCharDB`), печать в чат |
| `Core/Schema.lua` | **контракт формата маршрутов** (чистый Lua; общий с инструментами) |
| `Core/Compose.lua` | **сборка маршрута** из своих сегментов, сегментов библиотеки (`UseSegments`) и вставок (`AddInsert`); хранилище библиотеки (`AddLibrarySegment` / `AddLibraryData`). Чистый Lua, общий с инструментами (см. ниже) |
| `Core/Compat.lua` | единственное место, где вызываются игровые API квестов/карты/предметов/тренера/полётов. Все вызовы защищены (`nil`-проверки, `pcall` где нужно). Возвращает нормализованные значения |
| `Core/Registry.lua` | `FastesBoooy.RegisterRoute / AddSegment / AddRouteData / UseSegments / AddInsert / AddLibrarySegment / AddLibraryData`; хранение маршрутов и библиотеки; ленивая сборка (`Registry:Finalize`); выбор маршрута по фракции/расе/классу |
| `Core/Steps.lua` | обработчики действий: `IsActionDone(action, step, ctx)`, тексты/иконки для UI |
| `Core/Engine.lua` | активный маршрут, отфильтрованный список шагов, курсор, фоновые цели, ручные отметки, перемотка вперёд, реакции на события, колбэк `STEP_CHANGED` |
| `Core/Automation.lua` | автопринятие/автосдача квестов маршрута (QUEST_DETAIL / QUEST_PROGRESS / QUEST_COMPLETE / GOSSIP_SHOW / QUEST_GREETING), выбор награды, автодиалог; Shift — пауза автоматики |
| `Core/Waypoint.lua` | расчёт расстояния/направления до цели шага, нативная метка Blizzard (`C_Map.SetUserWaypoint` + `C_SuperTrack`) |
| `UI/StepFrame.lua` | окно шагов (текущий + следующие), прогресс целей, кнопки назад/вперёд/пропуск |
| `UI/Arrow.lua` | стрелка-навигатор с дистанцией |
| `UI/ItemButton.lua` | кнопка «использовать предмет» для поля шага `use` (см. ниже) |
| `UI/Options.lua` | панель настроек + `/fb` |
| `Locales/*.lua` | строки интерфейса (ruRU, enUS) |

## Общие сегменты и вставки (`Core/Compose.lua`)

Модули-библиотеки (`FastesBoooy_Horde`: `## Dependencies: FastesBoooy`) регистрируют
классово-нейтральные сегменты `FastesBoooy.AddLibrarySegment{...}` и имена
`FastesBoooy.AddLibraryData{...}` в одно хранилище `ns.Registry.library`
(`Compose.NewLibrary`): сегменты нормализуются `Schema.AddSegment` один раз (ошибки формата —
один раз, при регистрации), id сегментов и шагов уникальны во всей библиотеке. Модуль
маршрута (`## Dependencies: FastesBoooy, FastesBoooy_Horde` — клиент грузит библиотеку раньше)
вызывает `UseSegments(routeId, {...})` и `AddInsert(routeId, {after|before, steps})`.

* Первый такой вызов делает маршрут **составным**: его собственные сегменты переезжают в
  `route.own` (та же форма, что у маршрута: `segments/steps/stepById/segmentById`; туда же
  добавляют последующие `AddSegment`), а `route.segments/steps/stepById/segmentById` строит
  `Compose.Build`: свои сегменты (кроме названных в `UseSegments`) → элементы `UseSegments`
  (копии шагов библиотеки для этого маршрута — у разных маршрутов свои `index`; нормализованные
  `actions` общие, движок шаги не меняет) → вставки по порядку вызовов (после/перед якорем,
  после прежних вставок у того же якоря; шаги вставки получают сегмент якоря и id
  `<якорь>+<n>`, если id не задан). Данные библиотеки подмешиваются в `route.data` под данными
  маршрута. Маршрут без `UseSegments`/`AddInsert` не трогается вовсе.
* Сборка **ленивая**: вызовы только записывают, что сделать, и помечают маршрут `dirty`;
  `Registry:Finalize` собирает его при первом чтении — `Registry:Get/List/Matching/Select`,
  `Engine:BuildSteps` (после `ROUTES_CHANGED`) и `Engine:Start` (`PLAYER_LOGIN`, до вывода числа
  ошибок регистрации). Поэтому вставки можно регистрировать до или после `UseSegments`, а якорем
  может быть шаг библиотеки. Изменение библиотеки помечает все составные маршруты.
* Ошибки сборки (неизвестный сегмент библиотеки, неизвестный якорь, id шагов/сегментов,
  совпавшие только после сборки) записываются в `Registry.errors` **один раз** на маршрут
  (повторная сборка не дублирует сообщение). `UseSegments`/`AddInsert` до `RegisterRoute` —
  ошибка + очередь, как у `AddSegment`.
* Движок получает обычный плоский список шагов: фильтры, `bg` (сегмент якоря для вставок),
  `optional`, граница перемотки, брошенные квесты и `cursorHint` по id работают без изменений.
* Офлайн-инструменты загружают `Core/Schema.lua` и `Core/Compose.lua` в один `ns`
  (`tools/lib/route_loader.lua: Loader.LoadSchema`), модули-зависимости `FastesBoooy_*` из
  `## Dependencies`/`## RequiredDeps` — раньше модуля, в песочнице, каждый со своей таблицей
  `ns` — и собирают маршрут тем же `Compose.Build`. Итог в игре, в валидаторе, симуляторе и
  `gen_route_data` одинаков.

## Движок

1. При входе: выбирается маршрут (сохранённый для персонажа или `default`,
   подходящий по фракции/расе/классу).
2. Шаги фильтруются по `class/race/faction` → плоский список.
3. **Курсор** = первый шаг, который не выполнен и не `bg`. `bg`-шаги, через
   которые прошёл курсор, попадают в список «попутно», пока не будут выполнены
   или пока их квест не сдан/брошен (квест из `accept` ещё не взят — шаг
   остаётся). Перемотка на `bg`-шаги не действует, пока игрок в том же
   сегменте; когда курсор/перемотка ушли в более поздний сегмент, `bg`-шаги
   прошлых сегментов перематываются как обычные (их transient/`collect`
   считаются выполненными), чтобы холодный старт не возвращал давно пройденные
   цели. Выполненный `bg`-шаг с `collect`/transient-действиями запоминается
   (`FastesBoooyCharDB.bgDone`, только оптимизация).
4. Выполненность шага = AND по действиям (см. `docs/ROUTE_FORMAT.md`).
   Transient-действия отмечаются событиями, пока шаг текущий или в списке
   «попутно» (окно тренера/торговца — при закрытии, для шагов, наблюдаемых
   в момент открытия; карта полётов — при открытии; смена точки привязки;
   прибытие). Клиент шлёт и старое событие (`TRAINER_CLOSED` и т. п.), и
   `PLAYER_INTERACTION_MANAGER_FRAME_*` — одно окно засчитывается один раз.
   **Перемотка** (`Engine:Evaluate`): граница = max(опорный шаг, сохранённая
   отметка самого дальнего шага `cursorHint`). Опорный шаг — последний не-`bg`
   шаг с действием `accept`/`turnin`/`complete`, все stateful-действия которого
   выполнены (или он отмечен вручную); `level` опорой **не** является (уровень,
   набранный раньше за счёт rested-опыта, не должен молча пропускать более ранние
   `sethearth`/`train`/`fp`), как и `abandon` (выполнен «пусто») и `collect`
   (предметы могут быть в сумках случайно). Шаги до границы: transient-действия и
   `optional` считаются выполненными; из stateful — только `collect` (предметы
   потрачены более поздней сдачей) и `accept` квеста, который бросает более
   поздний шаг маршрута (`abandonAfter[i]` → `ctx.abandonedLater`, иначе после
   `abandon` курсор вернулся бы к `accept`). Прочие stateful-действия всегда
   читаются из игры, поэтому холодный старт с пустыми SavedVariables приходит
   на верный шаг; неизвестны только transient-шаги после последнего опорного.
   **Брошенные игроком квесты** (`Engine.givenUp[q] = j` → `ctx.givenUp`,
   сравнивается с `ctx.index`). Квест «оставлен», если (а) более поздний не-`bg`
   шаг с его `complete`/`turnin` отмечен («Пропустить» / «Дальше») или `optional`
   и лежит до границы перемотки (`j` = этот шаг), или (б) игрок бросил его вручную —
   в любом порядке с «Пропустить» (`FastesBoooyCharDB.gaveUp`, `j` = следующий
   `accept` того же квеста или конец маршрута). Для (б) на `QUEST_REMOVED` (кроме
   `wasReplayQuest`) движок запоминает натуральный курсор и через 0,5 с
   (`Engine:GiveUpQuest`) проверяет, что квест не сдан (`Compat.IsQuestTurnedIn`:
   при сдаче приходят и `QUEST_TURNED_IN`, и `QUEST_REMOVED`) и не в журнале; пока
   проверка ждёт, квест удерживается до запомненного шага — курсор не мигает назад
   и автоматика не берёт квест. Если `accept` квеста лежит до курсора (запомненный
   натуральный курсор или `cursorHint`; иначе квест был взят заранее — ничего не
   делается) и в этом экземпляре квеста (до следующего `accept`) нет явного
   `abandon` (маршрут ведёт квест сам), невыполненные не-`bg` шаги, все действия
   которых — `complete`/`turnin` этого квеста, получают отметку `skipped` (их id —
   в `gaveUp[q].steps`, шаг `accept` — в `gaveUp[q].accept`), в чат — одна строка.
   Если всё уже покрыто отметками игрока / пройденными `optional`-шагами, запись не
   создаётся. Пока квест не в журнале и не сдан, его `accept` и (на не-`bg` шагах)
   `complete`/`turnin` до индекса `j` считаются выполненными: курсор не прыгает
   назад, автоматика не берёт квест снова, смешанный шаг (`turnin = { Q, R }`) ждёт
   только остальных действий, `bg`-шаг с его `accept` уходит из списка «попутно».
   Отметки гайда не служат опорным шагом перемотки (иначе отметка далёкой сдачи
   перемотала бы `go`/`train` перед ней). Запись и её отметки снимаются, когда квест
   снова взят вручную (`QUEST_ACCEPTED` или квест найден в журнале при пересчёте;
   кроме случая, когда его взяли для следующего `accept` того же квеста в окне
   автоматики — это уже новый экземпляр) или сдан, по «Назад» сразу после
   оставления или на одном из её отмеченных шагов, по `/fb reset`. Холодный старт
   с пустыми SavedVariables о брошенном квесте не знает: курсор встанет на его
   `accept` (как и после потери отметок «Пропустить»).
5. Пересчёт — по событиям квестов/опыта/сумок/зоны с троттлингом и по тикеру
   позиции (для `go/fly/hearth`).
6. Прогресс сохраняется по персонажу: id маршрута, ручные отметки, пропуски,
   брошенные вручную квесты (`gaveUp`).

## Кнопка предмета (`UI/ItemButton.lua`)

* Показывает предмет `use` текущего шага (если у шага его нет — первого активного
  `bg`-шага «попутно»), пока предмет есть в сумках; левый клик использует его.
  Глобальное имя `FastesBoooyItemButton`: макрос `/click FastesBoooyItemButton`
  (можно назначить на клавишу). Правой кнопкой — перетаскивание (если окна не
  закреплены), позиция — `FastesBoooyDB.frames.item`.
* Это защищённая кнопка (`SecureActionButtonTemplate`, атрибуты `type1 = "item"`,
  `item1 = "item:<id>"`, `RegisterForClicks("AnyUp", "AnyDown")` — срабатывает и при
  `ActionButtonUseKeyDown`). Она создаётся отдельным окном верхнего уровня (родитель и
  привязка — только `UIParent`): защищённый дочерний или привязанный к окну шагов кадр
  сделал бы защищённым и само окно шагов, а оно в бою прячется, меняет высоту и
  перетаскивается.
* В бою (`InCombatLockdown()`) атрибуты, показ/скрытие и перемещение защищённого
  кадра запрещены: изменения откладываются до `PLAYER_REGEN_ENABLED` (иконка и
  счётчик — обычные регионы — обновляются сразу). «Прятать в бою» срабатывает на
  `PLAYER_REGEN_DISABLED`, до начала блокировки. `/reload` в бою — кнопка создаётся
  после боя.

## Автоматизация (только квесты маршрута)

* Принимаются квесты из `accept` в окне «текущий шаг + N следующих» (+ фоновые).
* Сдаются квесты из `turnin` в любом месте маршрута, если квест выполнен.
* Награда выбирается автоматически, если вариантов ≤ 1 или задан `reward`;
  иначе автоматика останавливается и пишет в чат «Выберите награду за … сами» (окно
  награды остаётся открытым; внутреннее сообщение `REWARD_CHOICE_NEEDED(questID, n)` —
  для модулей, которые захотят его подсветить; ядро само ничего не подсвечивает).
* Удерживаемый **Shift** отключает автоматику на текущий диалог: Shift,
  нажатый при открытии окна (GOSSIP_SHOW / QUEST_GREETING / QUEST_DETAIL /
  QUEST_PROGRESS / QUEST_COMPLETE), действует до закрытия диалога с этим NPC
  (`GOSSIP_CLOSED` без продолжения, `QUEST_FINISHED`), даже если его отпустить.

## Проверка (без запуска игры)

| Команда | Что проверяет |
|---|---|
| `make lint` | luacheck со стандартом `forever`, сгенерированным из списков API клиента Forever: любой вызов несуществующей функции/поля API — ошибка |
| `make test` | busted: схема, движок, автоматика, навигация, UI на моке WoW API (мок разрешает только методы виджетов, существующие в Forever) |
| `make validate` | валидатор маршрутов по снимку БД Forever (составные маршруты — вместе с библиотеками-зависимостями; сообщения о шагах библиотеки помечены `[library …]`) |
| `make simulate` | «прогон» каждого маршрута через настоящий движок на моке: каждый шаг должен завершаться ровно тем действием, которое он требует (библиотеки грузятся в мок как зависимости, отдельно не прогоняются) |
